# 问答流程优化方案：从用户输入到生成回复

日期：2026-11-08

状态：方案已确认，分步实施中。第 0 步已完成，基线见 [2026-11-08-eval-baseline](../changes/2026-11-08-eval-baseline.md)；第 1 步已完成，见 [2026-11-08-failure-answers](../changes/2026-11-08-failure-answers.md)；第 2 步已完成，见 [2026-11-08-failed-turn-history](../changes/2026-11-08-failed-turn-history.md)；第 3 步已完成，见 [2026-11-08-direct-answers](../changes/2026-11-08-direct-answers.md)；第 4 步已完成，见 [2026-11-08-history-sql](../changes/2026-11-08-history-sql.md)；第 5 步已完成，见 [2026-11-08-column-check](../changes/2026-11-08-column-check.md)；第 6 步已完成，见 [2026-11-08-whole-table-schema](../changes/2026-11-08-whole-table-schema.md)

## 结论

这次优化有四个目标：

1. **多轮对话带上之前的 SQL**：每轮回答除了结论，还把这一轮的查询用途和 SQL 一起交给模型。不传查询结果的数据行。
2. **让模型拿到写 SQL 需要的字段，写错时一定能拦住**：字段由程序按表放进上下文，执行前校验字段，报错时直接给出正确候选。
3. **不需要查数的问题正常回答**：解释口径、解释上一轮结论、闲聊，不再报错。
4. **出错时用户也能拿到有用的信息**：超时、查询次数用完、SQL 一直写不对时，展示已经查到的结果、系统是怎么理解问题的、失败原因和下一步建议，而不是只给一行错误。

另外，**表结构要不要按字段裁剪，由评测结果决定**。模型效果够好就不加，见第五节。

整体原则：

- **不该让模型判断的，由程序做**：时间解析、表结构检索、关联路径、字段校验、数字核对。
- **模型负责理解问题、写 SQL、写结论**，需要时可以调用工具补查。
- **"字段不存在"由程序兜底，必须拦住**；**"字段存在但用错了"只能降低概率**，所以要让依据可见，并持续评测。
- **失败也是一种回答**：能给多少就给多少，并说清楚缺了什么。

## 一、现在的流程

```
用户问题 + 历史（只有问题和结论文字）
  → 程序：解析时间（time_parser）、关键词拦截敏感问题
  → 程序：检索一次（向量，失败退回关键词）
          表摘要（全部表，但没有字段） + top 6 字段 + 指标口径 + 历史案例 + 实体值
  → 模型：自动模式下判断走查询还是分析（router）
  → 查询模式：一个 ReAct Agent
     分析模式：拆步骤（planner） → 每步一个 Agent 并行执行 → 补查一次 → 汇总
     工具：run_sql（校验表名和危险语句后执行）、describe_table、search_semantic、decline_request
  → 程序：核对结论里的数字，不一致就改用模板结论；检查 SQL 日期和时间范围
```

### 现在的问题

| 问题 | 位置 | 后果 |
| --- | --- | --- |
| 历史只有问题和结论文字，没有 SQL | `frontend/src/lib/conversations.ts` 的 `buildHistory` | 追问"按渠道拆一下""把退款也加上"时，模型不知道上一轮怎么查的，口径和写法可能和上一轮不一致 |
| 失败或中途停止的回答不进历史，用户问题照样进 | 同上 | 历史里出现两条用户消息相连、中间没有回答，模型可能把两个问题都答了（和 11-05 追问答错是同一类问题） |
| 字段只给 top 6，提示词还说"只列出一部分" | `semantic/models.py` 的 `to_prompt_context`、`agent/pipeline.py` 第 11 条规则 | 模型要自己决定去查字段，常常先猜，见 [模型猜错字段名](模型猜错字段名.md) |
| 执行前只校验表，不校验字段 | `safety/validator.py` | 字段错误要等 MySQL 报 1054 才发现，再多一轮 `describe_table` |
| SQL 失败没有硬性的重试上限 | `agent/pipeline.py`（`max_iters` 只限制 Agent 轮数） | 极端情况下反复重写，耗时变长 |
| 表名和业务规则写死在提示词里 | `agent/pipeline.py` 第 2、5 条规则，`agent/planner.py` 的 `TABLES` | 换库或加表要改代码 |
| 模型没调用 `run_sql` 就记为失败 | `agent/pipeline.py` 的 `ask`（`select_execution` 返回空的分支） | "GMV 包不包括运费？""你能查什么？"这类问题直接报错"模型没有调用 run_sql 工具" |
| 出错时只发一行错误文字 | `agent/pipeline.py` 的 `_finalize`（出错时只发 `error` 事件）、`frontend/src/hooks/useChat.ts` | 前端只显示一行红字。时间范围、尝试过的 SQL、检索到的口径都看不到 |
| Agent 抛异常时，已经成功的查询被丢掉 | `agent/pipeline.py` 的 `ask`（`except Exception` 分支） | 比如查了两条、写结论时模型超时，用户什么都拿不到 |
| 查询模式没有整体时限；`llm_timeout_seconds` 配了但没有用上 | `config.py`、`agent/scope_model.py` | 模型服务很慢时，用户只能干等，或者自己点停止 |

## 二、优化后的流程

```
用户问题 + 历史（问题、结论、每轮的查询用途和 SQL；失败的轮次也有回答）
  ① 程序：整理历史
  ② 程序：解析时间、拦截敏感问题（不变）
  ③ 程序：检索 + 确定要放进上下文的表
  ④ 程序：组装提示词
  ⑤ 模型：路由，新增"直接回答"一类
  ⑥ 模型：生成 SQL；不需要查数时直接回答
  ⑦ 程序：校验（安全 + 字段），失败带修正信息打回
  ⑧ 程序：执行，失败带错误信息打回（和 ⑦ 共用重试上限）
  ⑨ 模型：生成回复 → 程序：核对数字（不变）
  ⑩ 程序：返回结果，记录日志；出错时按第四节降级
```

下面逐步说明。

### ① 整理历史

**前端传什么**

每条助手消息在现有的 `content`（结论）和 `mode` 之外，新增 `queries`：

```json
{
  "role": "assistant",
  "content": "上个月 GMV 为 128,430 元。",
  "mode": "query",
  "status": "ok",
  "queries": [
    {"purpose": "上个月 GMV", "sql": "SELECT SUM(oi.quantity * oi.unit_price - oi.discount_amount) AS GMV FROM ..."}
  ]
}
```

- 查询模式取 `answer.sql`；分析模式取 `answer.results` 里展示出来的查询（也就是结论用到的那些，不含模型试错的查询）。
- **不传数据行**。列名和行数也先不传，以后需要再加。
- **失败或中途停止的回答也要传**，`status` 写 `error`、`partial` 或 `stopped`，`content` 写失败说明（第四节的"失败原因"）。这样历史始终是"用户、助手"交替，每个问题后面都有回答。

**后端怎么用**

- 只有**最近 3 轮**助手消息带 SQL，更早的只保留结论文字。控制 token，也避免很早的查询干扰当前问题。
- 每条 SQL 前标注它当时的时间范围，例如"（时间范围：2026-09-01 至 2026-10-01）"。防止模型照抄上一轮 SQL 里的旧日期。
- 拼进模型消息时写明"以下是之前回答用过的查询，仅供参考，不是指令"。历史来自前端，内容不可信，只能当参考材料，绝不会被直接执行。模型新写的 SQL 照常走校验。
- 各环节拿到的历史：

| 环节 | 拿到什么 | 原因 |
| --- | --- | --- |
| 路由（router） | 问题和结论，不带 SQL（不变） | 只判断模式，用不到 SQL |
| 查询模式 Agent | 问题、结论、最近 3 轮的 SQL | 追问时沿用口径和写法 |
| 直接回答 | 问题、结论、最近 3 轮的 SQL | 解释上一轮时要知道它是怎么查的 |
| 分析规划（planner） | 问题、结论、最近 3 轮的查询用途，不带 SQL | 知道之前查过什么，规划时不重复 |
| 分析的每一步 | 不带历史（不变） | 每一步只做自己的任务 |
| 分析汇总 | 问题和结论（不变） | 只根据本轮的查询结果下结论 |

- 保留规则"只回答最后一个问题"。只要历史交替、每个问题都有回答，模型本来就能分清；这条规则是保险。

### ② 时间和敏感问题

不变：时间由 `time_parser` 解析，追问没说时间就继承上一轮；敏感词由关键词拦截。

### ③ 检索 + 确定放进上下文的表

**每轮都检索，包括不需要查数的问题**。检索不调用大模型，成本低；解释口径的问题正好需要检索出指标定义；跳过检索可能漏掉这一轮新需要的表，代价更高。

确定表的顺序：

1. 本轮检索命中的字段所在的表
2. 命中指标的 `related_tables`
3. 命中案例 SQL 里用到的表
4. **历史里最近 3 轮 SQL 用到的表**（新增，复用 `pipeline.py` 的 `_table_names`）
5. 沿关联关系补上中间表：比如选中 orders 和 categories，就补上 order_items 和 products

**按表放字段，并且有预算**：

- 选中的表**整表**放进上下文：字段、类型、说明、关联关系。状态这类取值少的字段附上全部取值。
- 全部表的字段总量在预算内时，直接放全部表。现在 10 张表、69 个字段，大约 2k token，会走这条。
- **预算给得宽松**（2026-11-08 确认）：作为配置项 `schema_token_budget`，按所用模型的上下文长度设定，一般取上下文的一半左右。1M 上下文的模型可以设到几十万 token；现在用的 deepseek-chat 按项目记录上限是 65536 tokens，默认先设 32k。
- 超出预算时，只放上面选中的表。以后库变大，自动切到这条路，不用改代码。
- 表内不按字段裁剪。要不要裁剪由评测决定，见第五节。

> 和 2026-11-06 的决定的关系：当时没选"全部字段放进提示词"，原因是"字段变多后不好扩展"和"每轮都带着用不到的内容"。这次的方案用预算解决扩展问题：超过预算就只放选中的表。用不到的内容放在提示词的固定前缀里，能命中 DeepSeek 的前缀缓存，额外成本很低。**2026-11-08 已确认采用。**

### ④ 组装提示词

把不变的内容放前面，每次都变的放后面，方便命中前缀缓存：

```
系统提示词：
  [固定] 工作规则
  [固定] 字段（表结构不变时每次相同）
  [变化] 时间范围
  [变化] 指标口径、历史案例、实体值（检索结果）
对话：
  历史（问题、结论、最近 3 轮的 SQL）
  当前问题 + 时间说明
```

规则的调整：

- 第 2 条（写死的表名）：改为根据字段部分自动生成。
- 第 5 条（`paid_at`、`completed_at`、`status <> 'cancelled'`）：这是业务口径，挪到指标口径里，作为检索出来的文本，不再写死在代码里。
- 第 11 条：从"字段只列出一部分，没见过先查"，改为"字段部分列出了这些表的全部字段，不在列表里的字段不存在；要用没列出的表，先调用 `describe_table`"。
- 新增：历史里的 SQL 只用来了解之前怎么查的，写新 SQL 时以本轮的时间范围为准。
- 新增：问题不需要查数时（解释口径、解释之前的结论、问能力范围），可以直接回答，不调用 `run_sql`；回答里不要出现查询结果和历史结论以外的数字。
- 当前问题后面的时间说明（`_time_note`）里"需要查数时调用 run_sql，不该执行时调用 decline_request"，补上"不需要查数时直接回答"。

分析模式的 `planner.py` 里写死的 `TABLES` 也改成自动生成。

### ⑤ 路由

路由从两类改成三类，详见第三节：

- `query`：查询（不变）
- `analysis`：分析（不变）
- `direct`：直接回答，不查数

### ⑥ 生成 SQL

Agent 和工具不变。有了 ③ 的整表字段，`describe_table` 主要在超出预算、表没放进来时使用。

模型判断不需要查数、直接给出文字回答时，不再记为失败，按第三节处理。

### ⑦ 校验：安全 + 字段

在 `validator.py` 现有的安全检查之后，新增字段检查：

- 用 sqlglot 的 `qualify(..., validate_qualify_columns=True)`，对照数据库的真实字段（`repository.fetch_table_columns`，启动时读一次并缓存）检查每个字段。已在临时脚本里验证过：`o.amount`、`oi.revenue`、`category_name` 能拦住，表别名、CTE、`ORDER BY` 别名都能正常通过。
- 报错时直接给出修正信息，不让模型再去调用 `describe_table`：

  ```
  字段不存在：ad_daily_stats.cost。最接近的字段：spend。
  ad_daily_stats 的字段：id, campaign_id, stat_date, impressions, clicks, spend, attributed_gmv, attributed_orders
  ```

- 除"字段不存在"以外，qualify 解析失败的一律放行，交给数据库执行。**宁可放过，不误拦合法 SQL。**
- 表白名单 `ALLOWED_TABLES`、schema 名 `safe`、方言 `mysql` 改为从配置和数据库读取。

### ⑧ 执行

- 数据库报 1054 时，和 ⑦ 一样附上那张表的真实字段和最接近的字段名。
- **重试上限**：一次问答里连续失败（校验或执行）达到 `sql_max_retry`（现在是 3）次后，`run_sql` 返回"不要再试，如实告诉用户没查出来"，然后按第四节降级。分析模式的每一步沿用现有的查询次数上限。

### ⑨ 生成回复

不变：查询模式的结论要通过 `verify_summary`，不通过就改用模板结论；分析模式用 `unverified_numbers` 找出没核对上的数字，作为警告展示。

因为历史里不传数据行，核对范围不用改：结论里的数字只会来自本轮的查询结果。直接回答的数字核对见第三节。

### ⑩ 返回和日志

- 返回结构增加第三、四节的新状态和 `failure` 字段。前端把这一轮的 SQL 存进会话，下一轮由 `buildHistory` 带上。
- 日志新增：这一轮带了几轮历史 SQL、放进上下文的表和来源（检索 / 指标 / 案例 / 历史 / 关联补全）、字段校验拦截了几次、失败类型。

## 三、不需要查数的问题

### 有哪些

| 类型 | 例子 | 需要什么 |
| --- | --- | --- |
| 解释口径 | "GMV 包不包括运费？" | 指标口径（检索） |
| 解释上一轮 | "刚才为什么说渠道 A 拖了后腿？" | 历史结论和历史 SQL |
| 改写上一轮 | "把上面的结论写成一段话发给老板" | 历史结论 |
| 能力范围、闲聊 | "你能查什么？""你好" | 表摘要 |

### 怎么改

**1. 路由增加 `direct`**

- `router.py` 的提示词和 `parse_route` 增加第三类，附上示例。拿不准时仍偏向查数（`query` 或 `analysis`）：不需要查数却去查了，只是慢一点；需要查数却直接回答，用户拿不到数据。
- 走 `direct` 时，用一个不带 `run_sql` 的 Agent 回答，输入是历史、检索到的口径和表摘要。

**2. 查询和分析模式下，也允许不查数直接回答**

用户手动选了查询模式，问的却是口径问题，或者自动模式的路由判断错了，模型都可能不调用 `run_sql` 就直接回答。现在这种情况记为 `error`，改成：

- 模型给出了文字回答、没有任何查询：返回这段文字，状态记为 `text`。
- 模型既没有回答，也没有查询：按第四节"没有任何结果"处理。

**3. 数字核对**

直接回答里出现的数字，只能来自历史结论、检索到的口径说明或用户的问题。其他数字作为警告展示："这些数字没有查询依据：……"。复用现有的 `unverified_numbers`，把历史结论和口径文本作为核对来源。

**4. 前端**

`text` 状态的回答卡片只显示文字结论，不显示表格、图表和 SQL 标签页。

## 四、出错时也给用户有用的信息

### 原则

- **后端总是返回完整的回答卡片**（`answer` 事件），带上状态和失败说明。`error` 事件只留给传输层的问题：网络断开、服务崩溃、返回的数据无法解析。
- **能给多少就给多少**：已经查到的结果要展示，系统怎么理解问题的要展示，尝试过的 SQL 要能看到。
- **说清楚缺了什么、为什么、接下来可以怎么做**。

### 新增状态和字段

| 状态 | 含义 |
| --- | --- |
| `ok`、`empty`、`refused` | 不变 |
| `text` | 不需要查数，直接回答（第三节） |
| `partial` | 有一部分查询成功了，但没能完整回答 |
| `error` | 没有拿到任何查询结果 |

新增 `failure` 字段，有失败时填写：

```json
{
  "kind": "timeout",
  "message": "模型生成结论时超时，下面是已经查到的结果。",
  "suggestion": "可以稍后重试，或者把问题拆小一点。"
}
```

`kind` 的取值：`timeout`（超时）、`sql_failed`（SQL 一直写不对）、`model_error`（模型服务出错）、`no_answer`（模型没有给出任何回答）、`step_failed`（分析有步骤没查到数据）、`unexpected`（其他异常，例如代码问题）。

> 第 1 步实施时的调整：查询次数用完不算失败，只加一条警告，所以去掉了 `query_limit`；新增 `step_failed` 和 `unexpected`，避免把代码异常说成模型服务出错。

### 每种情况怎么处理

| 情况 | 现在 | 改后给用户什么 |
| --- | --- | --- |
| 模型没调用 `run_sql`，但给出了文字回答 | `error`："模型没有调用 run_sql 工具" | `text`，按第三节处理 |
| SQL 连续失败达到上限 | `error`，只有最后一次的错误原文 | `error` + 回答卡片：时间范围、用到的表、相关口径、最后一次尝试的 SQL、用大白话说的失败原因（如"数据库里没有'成本'这个字段，最接近的是广告花费 spend"）、建议换个说法 |
| Agent 抛异常（模型超时、调用失败），**已经有查询成功** | `error`，已经成功的查询被丢掉 | `partial`：展示已有的查询结果，结论用模板生成，说明"模型生成结论时出错，下面是已经查到的数据" |
| Agent 抛异常，**还没有查询成功** | `error`，只有异常文字 | `error` + 回答卡片：时间范围、用到的表、相关口径、失败原因、建议 |
| 整体超时（新增） | 查询模式没有整体时限 | 到时间后停止。有结果按 `partial`，没有按 `error` + 回答卡片 |
| 分析模式查询次数用完 | 模型基于已有结果作答（已有） | 保留；结论下方注明"查询次数已用完，分析基于以下 N 条查询" |
| 分析模式某一步失败 | 汇总时说明缺了哪部分，计划里标出失败的步骤（已有） | 保留；回答状态记为 `partial` |
| 分析汇总超时 | 改用模板结论（已有） | 保留；卡片上注明"结论由模板生成" |
| ReAct 轮数用完 | AgentScope 会强制模型给出文字回答 | 有查询结果按正常处理；没有查询按第三节的 `text` 或 `error` 处理 |
| 模型服务不可用（没配置、key 错、网络不通） | `error` | `error` + 回答卡片，`kind` 为 `model_error`，说明是模型服务的问题，提示到设置页检查，不是问题本身问错了 |
| 查询结果为空 | `empty`（已有） | 保留；补充说明查询条件（时间范围、筛选值），方便用户调整 |

### 整体时限

- 把 `llm_timeout_seconds` 真正接上：作为单次模型调用的超时，传给模型客户端。
- 新增整体时限，作为配置项：查询模式 `ask_timeout_seconds` 120 秒，分析模式 `analysis_timeout_seconds` 180 秒（2026-11-07 评测里分析最长 81 秒）。到时间后取消 Agent，按上表处理已有结果。
- 分析模式已有的规划、补查、汇总超时保持不变。

### 前端

- `AnswerCard` 根据状态显示：`partial` 显示黄色提示条加已有的结果；`error` 显示失败原因、建议，以及"我是怎么理解这个问题的"（时间范围、用到的表、口径），尝试过的 SQL 放在 SQL 标签页。
- 卡片上提供"重试"和"用分析模式重新回答"（已有）。
- `useChat.ts` 里的 `error` 事件处理保留，只用于传输层的失败。

## 五、表结构裁剪：由评测决定

### 现在的判断

不做。现在 10 张表、每张表不超过 11 个字段，整表放进上下文约 2k token，裁剪几乎没有收益。字段级裁剪还有召回风险：漏掉一个需要的字段，模型就会去猜；关联键、时间字段、状态字段在用户的问题里通常不会出现，最容易被裁掉。

### 什么时候重新评估

满足任一条件时：

- 接入更大的数据库后，选中的表加起来超过预算（`schema_token_budget`）
- 出现宽表（一张表超过 30 个字段）
- 评测里"选错字段""选错表"的失败明显变多

### 怎么评估

1. 第 0 步给失败的评测题标注失败类型：字段不存在、字段用错、表选错、口径错、时间错、其他。
2. 在大库上准备评测集，分别跑两种做法：A 整表（不裁剪）、B 只对宽表裁剪（保留主键、外键、时间字段、状态字段和检索命中的字段，注明"还有 N 个字段没有列出，需要时调用 `describe_table`"）。
3. 每种做法至少跑两次，减少随机波动的影响。

### 怎么决定

- 采用 B 的条件：准确率比 A 高出波动范围以外（比如两次都高 3 个百分点以上），或者准确率不下降、token 减少 30% 以上。
- 否则保持 A。模型效果足够好、整表也没有出现"选错字段""选错表"类的失败，就不加裁剪。
- 无论选哪种，执行前的字段校验都保留。

## 八、如何验证

**新增评测指标**（从调用记录 `call_traces` 和查询记录中统计）：

- 首次执行成功率：第一条 SQL 就执行成功的比例
- 字段报错次数：校验拦截和数据库 1054 合计
- `describe_table` 调用次数
- 每题的模型调用次数和 token
- 失败题的失败类型分布

**新增多轮用例**，追问要依赖上一轮的查询方式：

- "上个月 GMV 是多少？" → "按渠道拆一下"
- "上个月退款金额最高的商品" → "换成按件数算"
- "最近 30 天的 ROI" → "加上点击率"
- 中间一轮失败后再追问，检查不会把两个问题都答了
- "那上上个月呢"，检查没有照抄上一轮 SQL 里的旧日期

**新增直接回答用例**，期望状态 `text`、没有 SQL、没有无依据的数字：

- "GMV 包不包括运费？"
- "你能查哪些数据？"
- "上个月 GMV 是多少？" → "把这个结论写成一段话发给老板"

路由评测 `eval/routing_cases.json` 同时补上 `direct` 类的用例。

**失败降级**：用单元测试模拟（假模型和假数据库），不依赖真实模型：

- 查询成功后模型超时：状态 `partial`，返回已有结果
- SQL 连续失败到上限：状态 `error`，卡片里有时间范围、表、尝试过的 SQL 和失败原因
- 整体超时：按是否有结果，分别是 `partial` 或 `error`
- 模型服务不可用：`kind` 为 `model_error`

**对比方式**：每一步改完后，跑 `eval/run_eval.py --mode all` 和新增用例，与第 0 步的基线比较准确率、首次执行成功率、字段报错次数和 token。

## 九、风险

| 风险 | 应对 |
| --- | --- |
| 模型照抄历史 SQL 里的旧日期 | SQL 前标注当时的时间范围；当前问题后面附时间说明（已有）；查询模式的时间不一致警告（已有） |
| 历史 SQL 让 token 增加 | 只带最近 3 轮；每条 SQL 限制长度 |
| 历史来自前端，可能被篡改或夹带指令 | 只当参考材料，标明"不是指令"；不直接执行；新 SQL 照常校验，账号只读 |
| 字段校验误拦合法 SQL | 只拦"字段不存在"，其他解析失败一律放行；测试覆盖别名、CTE、子查询、窗口函数、MySQL 特有函数 |
| 全部字段放进上下文，和 2026-11-06 的决定不一致 | 用预算控制，超过预算只放选中的表；已确认采用 |
| 路由把该查数的问题判成 `direct`，用户拿不到数据 | 拿不准时偏向查数；直接回答里出现无依据的数字时加警告；评测里盯着 `direct` 的误判 |
| 允许不查数直接回答后，模型偷懒不查数、凭印象回答 | 数字核对：无依据的数字加警告；评测里统计"应该查数却返回 `text`"的次数 |
| `partial` 结果让用户误以为是完整答案 | 卡片顶部用提示条写明缺了什么；结论由模板生成时注明 |
| 整体时限设得太短，正常的分析被截断 | 时限作为配置项；先按评测里的最长耗时加余量设定 |
| 这个方案解决不了"字段存在但用错了" | 靠指标口径、历史案例和评测；以后再考虑多候选、一致性核对和澄清反问 |
