# 按表的混合检索、重排和补全

日期：2026-11-09

## 做了什么

这是[问答流程优化方案](../问题记录/问答流程优化方案.md)的 8.2：新增按表检索，一次检索给出一个问题需要的表。这一步只写检索本身，用召回率评测验证；接进问答、交给模型调用是 8.3 的事，**线上的问答还没有用它**。

**按表检索**（`backend/app/semantic/table_search.py`，新增）

1. 混合检索：向量和关键词两路一起跑，分别检索字段、表摘要、指标和案例。每一路的字段命中按"第一次出现"折算成表的排序，案例按它的 SQL 用到的表折算，各个排序用 RRF（按名次加分）合并。向量不可用时只用关键词，并注明原因。
2. 重排：合并后的前 `rerank_candidates`（20）张表交给重排模型，每张表写成"表名、摘要、字段和说明"，保留前 `search_top_tables`（5）张。没有配置重排模型、调用失败或超时，按检索的排序继续，并注明原因。
3. 补全，只加表不删表：
   - 外键指向：选中的表里命中的字段如果是关联字段，补上它指向的表。比如问"各渠道"命中 `orders.channel_id`，补上 `channels`。
   - 口径需要：排名前 2 的指标的 `related_tables`。
   - 实体所在：问题里原样出现的实体值所在的表，例如"直播带货"补上 `channels`。向量找到的相近值不补表，原因见下面的验证。
   - 关联补全：沿关联图补上把这些表连起来的中间表。
4. 返回每张表和它被选中的原因（检索命中、重排选中、外键指向、口径需要、实体所在、关联补全），以及命中的指标、案例和实体值。

**重排模型**（`backend/app/rerank/`，新增）

- `DashScopeReranker`：调用阿里云百炼的原生重排接口（`https://dashscope.aliyuncs.com/api/v1/services/rerank/text-rerank/text-rerank`）。报错时说明 HTTP 状态和错误码，不会带出 key。
- `FakeReranker`：测试用，按相同的字数打分。
- `build_reranker`：按配置生成；`RERANK_API_KEY` 为空时用 `EMBEDDING_API_KEY`（都是百炼的 key）；`RERANK_PROVIDER=off` 关闭重排。
- `backend/app/providers.py`、`config.py`、`.env.example`：新增 `rerank_provider`（默认 `qwen`）、`rerank_endpoint`、`rerank_model`（默认 `qwen3.7-text-rerank`）、`rerank_api_key`、`rerank_timeout_seconds`（5 秒）、`rerank_candidates`（20）、`search_top_tables`（5）。

**元数据**

- 实体字段标记：`semantic_schema_items` 新增 `is_entity`（`data/initdb/02_app_schema.sql`、`models.py`、`repository.py` 的读取和同步）。种子数据给商品名、类目、渠道、省份四个字段打上标记。已有的数据库启动时自动补上这个字段（`repository.ensure_entity_column`，在 `bootstrap.py` 连库那一步执行，早于同步种子数据）。
- `repository.fetch_entity_values` 改为读取打了标记的字段，不再写死 4 条 SQL。每个值记下它在哪张表的哪个字段，表名和字段名只接受普通的名字，并按数据库的写法加引号。
- `repository.fetch_foreign_keys`：读数据库声明的外键。`schema_context.py` 新增 `hint_keys`（从 `join_hint` 读出字段之间的关联）和 `pointed_tables`，`join_graph` 合并数据库外键和 `join_hint`。`table_names` 从 `agent/tools.py` 挪到这里，`tools.py` 照常导出。
- 向量索引：实体值的记录带上表名和字段名（`indexer.py`）。索引新增版本号 `INDEX_VERSION = 2`，`bootstrap.index_is_current` 发现版本不同时，启动时自动重建索引。

**评测**

- `eval/retrieval_eval.py`：召回率评测新增 4 种做法：混合检索、混合加补全、混合加重排、混合加重排加补全。每道题记录耗时和每张表被选中的原因；结果里记下重排模型，以及重排没有生效的原因。
- `eval/run_eval.py`：`--mode retrieval` 用配置的重排模型。

测试：

- 新增 `backend/tests/test_table_search.py`，24 个测试：RRF、按字段排表、四种补全、只按原样出现的值补实体表、重排决定选哪些表、只把前 N 张候选交给重排、重排失败和没有配置时按检索排序、没有向量时用关键词、案例 SQL 指向的表、外键和 `join_hint`、实体值从打了标记的字段读（用 SQLite）、表名不合法时拒绝、种子数据的标记；重排适配层的请求格式、4 种错误、没有文档时不发请求、按配置生成。
- `test_bootstrap.py`：启动时补上 `is_entity`；索引版本不同时视为过期。
- `test_retrieval_eval.py`：评测覆盖新的 4 种做法。
- `test_column_check.py`：跳过召回率评测的结果文件（里面没有 SQL）。上一次提交后这个测试就会失败，因为 8.1 新加的结果文件格式不同，跑测试时那个文件还没生成，所以当时没发现。

## 为什么做

8.1 的基线显示，现在的检索有两类问题：向量检索漏掉渠道、商品这类维度表；又在 44/64 道题里带上了不需要的广告表。两路检索漏的题又几乎不重叠。第 8 步要让模型只拿到检索到的表，检索必须先找全。

## 有什么用

- 一次检索就能拿到问题需要的表，召回率从 84.4%（54/64）提高到 98.4%（63/64）。
- 每张表都写明了为什么被选中，8.3 交给模型时可以一起给出，排查问题也方便。
- 换库时，外键、实体字段、指标都从数据库和语义层读，不用改代码。

- 调参过程（结果文件也在 `eval/results/`）：
  - **实体补全只认原样出现的值**：一开始向量找到的相近实体值也补表，平均每题多带 0.8 到 0.95 张用不上的表（问题里没有提商品，也会近似匹配到某个商品名）。改成只认原样出现的值后，重排加补全仍然是 63/64，平均表数从 6.9 降到 6.1，token 从 1961 降到 1779。
  - **重排模型**：改实体补全之前对比过两个模型。`qwen3.7-text-rerank` 63/64、6.9 张表、1.9 秒；`qwen3-rerank` 64/64、7.3 张表、2.6 秒，差别不大，默认用更快的 `qwen3.7-text-rerank`。`qwen3-rerank` 第一次跑时遇到网络问题（SSL 握手超时），结果作废，重跑一次，那次 128 次重排里有 1 次超时。
  - **选几张表**：选 3 张时平均 4.8 张表、1428 token，但找全降到 61/64，多漏了 n08（`orders`）和 c04（`categories`、`products`）。这一次也有 1 次重排超时，那道题按检索排序。漏表会直接答错，多带一张表只多花一些 token，所以默认保持 5 张。

需要说明的内容：

- **线上问答还没用到按表检索**，要到 8.3 接入。这一步改动影响到线上的只有两处：
  - **实体值改为按 `is_entity` 标记读取**：商品名不再只取在售商品，下架商品的名字也会匹配到。
  - **提示词里实体值的写法变了**：从 `product: 某商品` 变成 `products.name: 某商品`。
  
  这一步没有跑完整的问答评测，只用上面一道题确认问答正常。
- **找得全，但带得多**：这个库一道题平均只需要 2 张表，默认配置平均放 6.1 张，每题约 4.1 张用不上。表只有 10 张，选 5 张再补全，已经占了大半。要看重排的真实效果，需要 8.4 表更多的测试库。
- **只靠重排去掉多余的表并不灵**：同样选 5 张，"混合 + 重排"的召回比"混合"还低（56 对 58）；加上补全后才比不重排的好（63 对 61）。只跑了一次，差 2 题，可能在波动范围内。
- **重排每次检索多花约 1.5 秒**，8.3 接进问答后会让每题变慢，要在完整评测里统计耗时。
- **还剩 n05 一题没找全**："今天有什么需要我注意的？"这一题，标注需要 `orders` 和 `order_items`，检索只找到了 `orders`。
- **数据库外键这条路没有真实数据验证过**：现在的库没有声明外键，只读账号也只能看到 `safe` 视图，所以 `fetch_foreign_keys` 读不到东西，关联全靠 `join_hint`。方案里原本写了"从视图的底层表读外键"，只读账号没有权限，没有做。读外键这部分只有单元测试。
- 召回率每种配置只跑了一次。检索本身是确定的，但重排模型和网络会带来少量波动。
