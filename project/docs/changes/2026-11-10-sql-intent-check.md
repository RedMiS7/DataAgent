# SQL 执行前和意图对照

日期：2026-11-10

对应优化计划 2 的第 6 步的后半部分：2.3 SQL 和意图的一致性检查。前半部分是 2.2，见 `2026-11-10-intent-and-clarify.md`。

## 做了什么

**对照模块**：`backend/app/agent/sql_intent.py`（新增）

用 sqlglot 解析模型写的 SQL，在执行之前和问题的意图逐项对照：

| 检查 | 怎么判断 | 不通过的例子 |
| --- | --- | --- |
| 时间 | SQL 里的日期要包含时间范围的起止日（结束日写成最后一天也算）；有对比期时，对比期的日期也要有。用户说了时间、SQL 却没有任何日期，也不通过。没说时间（按默认 30 天）的问题，SQL 没写日期就不查 | 问“上个月”，SQL 写成本月 |
| 指标的表 | 意图里的指标在语义层里有 `related_tables` 时，SQL 要用到其中每一张表 | 问 GMV，SQL 只查了 orders，没用 order_items |
| 比值 | 指标的公式里有除法（`/`、“除以”），或结果形式是比率时，SQL 里要有除法 | i02：问退货率，SQL 只查了退款金额和 GMV 两列 |
| 分组 | 意图里有对应字段的维度时，最外层 GROUP BY 要按它分组。`GROUP BY 1`、按别名分组、按同一张表的其他字段（如 id）分组都算 | 问“各渠道”，SQL 没有按渠道分组 |
| 筛选 | 意图里绑定了字段的筛选值，要出现在 SQL 的字符串常量里，`=`、`IN`、`LIKE` 都算 | 问“直播带货渠道”，SQL 没有这个条件 |
| 结果形式 | 前 N 名：要有 ORDER BY 和 LIMIT，并且 LIMIT 不超过 N。一个数值：最外层不能分组（没有维度时）。趋势：要有分组 | f05：问“哪个卖得最差”，SQL 是 LIMIT 10 |
| 关联后计数 | 同一层 SELECT 里关联了一对多的两张表时，用 `COUNT(*)` 或 `COUNT(一边.字段)` 数“一”边，并且没有 DISTINCT | 订单关联订单明细后，用 `COUNT(*)` 数订单 |

- **一对多关系**：从语义层的关联说明里读，例如 `关联 safe.order_items.order_id`。两边中字段是 `id` 的一边算“一”。业务库是视图，读不到主键，所以用这个约定。两边都不是 `id` 的关联（如“与 safe.shipments.province 对应”）不当作一对多。
- **`COUNT(*)` 的判断**：只有在 FROM 后面第一张表是“一”边时才算错。例如 `FROM products JOIN categories` 时，`COUNT(*)` 数的是商品，商品一边每行只出现一次，所以不算错。
- **检查哪条 SQL**：检查模型自己写的 SQL，不检查安全校验加过 LIMIT 的版本。否则“前 N 名没写 LIMIT”永远查不出来。
- **解析失败**：SQL 解析不了时不检查，交给数据库执行。安全校验已经放行了这条 SQL。

**接入**
- `backend/app/agent/tools.py`：
  - `run_sql` 在安全校验和“没检索过的表”检查之后、执行之前调用对照。
  - 不通过时，SQL 不执行，把原因返回给模型，在存档里记一条 `blocked`。处理方式和安全校验拦截时一样，也计入连续失败次数。
  - **同一类不一致，对一个问题只拦一次**。第二次再出现就放行，并在回答里加一条警告：“SQL 可能和问题不一致：……”。计划书里没有这一条，是我加的，目的是检查误判时不会把问题卡死。
  - 时间这一类放行时不另加警告，因为回答里原来就有“查询用的日期和显示的时间范围不一致”。
- `backend/app/agent/pipeline.py`：
  - 意图检查完之后，用意图、时间范围和语义层建好对照条件，放进运行上下文。
  - 查询模式做全部检查。分析模式只做“关联后计数”：分析的每条查询只看一个切面，拿整个问题的意图去对照会误报。
  - 没有拿到意图时，也只做“关联后计数”。
  - 放行时的警告会写进查询模式、分析模式和部分完成的回答。

**评测**
- `backend/app/evaluation/runner.py`：每题记录被对照拦下的 SQL 次数（从存档里按错误信息的开头识别），以及回答里放行警告的条数。
- `backend/app/evaluation/report.py`：每组输出“SQL 和意图对照：拦下 X 次（Y 题），第二次不一致放行并警告 Z 次”。

**测试**
- 新增 `backend/tests/test_sql_intent.py`（25 个），用的是电商数据集真实的语义层：
  - 回归用例：
    - i02 当时执行的 SQL 会因为“没有做除法”被拦下，改成比值后通过；
    - f05 的 `LIMIT 10` 会被拦下，改成 `LIMIT 1` 后通过。
  - 每项检查各有正例和反例，包括 `BETWEEN` 写法、`GROUP BY 1`、按别名或 id 分组、`IN` 和 `LIKE` 筛选、子查询里的计数、数“多”边、`COUNT(DISTINCT)`。
  - 分析模式和没有意图时只做关联检查；SQL 解析不了时不检查。
  - 流程里：不一致的 SQL 先被拦下，改过的 SQL 才执行；同一类不一致第二次出现时放行，回答带一条警告。
- `backend/tests/test_evaluation_intent.py`：加了 2 个计数的测试，报告输出的测试也加了这一行。
- `backend/tests/test_intent.py`：测试里的 SQL 原来不算比值、日期也和意图对不上，现在会被新检查拦下，所以按各自的意图改了 SQL。

## 为什么做

2.2 之后，程序知道了问题问的是什么，但模型写出的 SQL 还可能答的是另一个问题。评测里的 i02、f05 就是这样：
- i02：SQL 只查了退款金额和 GMV，比率是模型在结论里自己算的；
- f05：问“哪个卖得最差”，SQL 返回了 10 行。

这类错误在 SQL 执行前就能从语法树上看出来。和 SQL 安全校验一样，退回给模型改，比答完再提醒要好。

拦截只拦一次，是因为这些规则是启发式的。比如一对多关系是按“字段叫 id”推断的，可能判错，判错时不能让问题答不出来。

## 有什么用

- 时间、指标的表、比值、分组、筛选、结果形式、关联后计数这几类错误，在执行前就会被退回给模型修正。
- 第二次仍然不一致时照常回答，但用户会看到警告，知道这条 SQL 可能有问题。
- 评测能看到每组被拦下多少次、放行多少次，用来判断规则是否偏严。

    - 这是判分对“百分数还是小数”的处理问题，不是这一步的问题。评测 13 里模型恰好乘了 100，就通过了。语义层退货率的公式是“退款金额 / GMV”，没有说要不要乘 100。

  - 误拦的比例：要看全量评测里的“拦下 X 次”和这些题最后是否通过，由你来跑。
  - DABench：没有在它上面跑。DABench 的关联说明只有 `orders.product_id` 和 `inventory.product_id` 互相关联，两边都不是 `id`，所以 DABench 上不会做关联后计数的检查。

## 已知的影响

- 规则误判时，模型会多改一次 SQL，多一次模型调用。第二次就放行，不会卡死。
- 指标要求用到 `related_tables` 的每一张表。查询模式里，一个问题问了两个指标、模型分成两条 SQL 查时，第一条可能因为缺另一个指标的表被拦下一次。
- 一对多关系按“字段叫 id 的一边是一”推断，数据集不按这个约定命名时，这项检查会不准。
- 判分不区分百分数和小数，让 i02 这类比率题的分数跟着模型的写法变化。可以在判分里把乘以 100 的情况当成相同，或者在语义层的公式里写清楚。这属于计划 1 的 1.4，这一步没有改。
