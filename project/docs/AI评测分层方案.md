# DataAgent 分层 AI 评测方案

日期：2026-11-09
状态：方案，待确认（尚未改代码、评测集和提示词）

参考：

- [问答流程优化方案](问题记录/问答流程优化方案.md)：①～⑫ 的问答链路，以及第四、八节已有的评测指标
- `DB/description.md`：火山引擎 Data Agent 评测体系（业务关联性、可操作、前瞻性；达标级 / 工业可用级 / 专业研究级）
- `DB/DABench.csv`：10 道 DABench 题（归因 8、自由提问 2；中等 8、困难 2；全部 `is_open=是`），数据已导入 `dabench` 库
- [Redis 接入方案](Redis接入方案.md)：SQL 结果、embedding、rerank 缓存和限流

## 结论

1. **按链路分层评测，每层只回答一个问题**。从"程序部分对不对"到"业务上有没有用"共 7 层（L0～L6），外加横向的稳定性、成本和线上评测。越底层越确定、越便宜，每次提交都跑；越上层越贴近业务、越贵，按需跑。
2. **端到端失败要能定位到层**。用 `call_traces` 和 `ToolProbe` 找出"第一个出错的环节"（路由 → 检索 → SQL → 执行 → 结论），并用"给标准答案"的对照实验（例如直接给出正确的表）量出每一层各丢了多少分。
3. **DABench 归因题不能只比 SQL**。把 `root_cause_gt` 拆成原子因素，由程序核对数字、由 LLM 评委判断因素是否命中，再用人工标注校准评委。10 道题太少，用"在数据副本里注入异动"的办法批量造出答案确定的归因题。
4. **结果要可比**：每次评测记录 git commit、提示词版本、模型、`schema_mode`、是否开缓存；准确率至少跑 3 次，报均值和波动，并列出"新通过 / 新失败"的题。
5. **不同来源的题分开计分**。现在 85.1% 的总分里混着路由题、安全规则题和重复计分的归因题，只算电商数据题是 69.2%。每道题标注数据集和类型，只在同一数据集的数据题里算准确率；DABench 第 101 题的前提和数据不符，移出主分（见第一节）。
6. **Redis 和 Kafka 解决的是评测和线上暴露出来的工程问题**，不替代 Agent 编排：Redis 管缓存、限流、模型并发配额、会话、熔断；Kafka（或第一阶段用 Redis Streams）管长任务异步化、日志和 trace 出请求路径、线上评测、反馈回流、语义层变更通知。每项都给出用哪一层评测来证明效果，见第五节。

#### 3. 计分规则

已实现，见 [2026-11-09-eval-score-groups](changes/2026-11-09-eval-score-groups.md)。和下面写的不同的一点：问答题的 id 没有加前缀（保持和以前的结果文件可对照），只把路由题改成 `rt01`～`rt33`；DABench 的核对记录在 `eval/dabench_reviews.json`。

- **每道题标注 `dataset` 和 `kind`**：
  - `dataset`：`ecommerce_demo`、`dabench`、`dabench_synth`（异动注入题）、`none`（和数据无关）。
  - `kind`：`data`（查数据并比对结果）、`routing`（只测路由）、`rule`（危险 SQL 这类规则）、`behavior`（拒答、注入、直接回答）。
- **只在同一个 `dataset`、同一个 `kind` 里算准确率**，不出跨数据集、跨类型的总分。报告的第一行是当前数据集的数据题分数；规则题、安全题作为硬门槛，只报"全过 / 第几题没过"。
- **按当前连接的业务库自动筛题**：`settings.mysql_business_db` 是 `safe` 就只跑 `ecommerce_demo` 的数据题，是 `dabench` 就只跑 DABench 的题。电商题跑在 DABench 实例上必然全错，不能计入。
- **存疑题**（前提和数据不符、标准答案有争议）照常跑、照常记录，但不进任何分数；在报告末尾单独列出，人工复核后再决定改题、修正答案还是删除。
- **id 全局唯一**，带上来源前缀，例如 `route-01`、`ec-q01`、`dab-48`。
- **同一道题只计一次分**：写死的退货率归因流程（`evaluate_attribution`）是另一个被测对象，题目单独建 `kind=pipeline_attribution`，不和问答链路共用 a01～a04。
- 题目文件里每道 DABench 题记录核对结果（前提是否成立、核对用的 SQL 和数值），数据重新导入后重新核对一遍。

## 二、分层总览

```
                 L6 线上评测：抽样评委、用户反馈、漂移告警         （持续）
           ┌──── L5 分析与归因：根因命中、意图完成、框架遵从、建议可用  （每周 / 大改前）
           │     L4 多轮会话：继承时间、沿用口径、失败后恢复           （合并前）
 端到端 ───┤     L3 单轮问答：执行结果正确、状态正确、拒答正确          （合并前）
           │     L2 单个模型环节：路由、规划、SQL 生成、结论生成         （改提示词时）
           └──── L1 检索：表召回、口径和实体命中、返回大小               （改语义层/检索时，不调大模型）
                 L0 程序部分：时间解析、安全校验、字段校验、补全、数字核对、降级 （每次提交，不调任何模型）

横向：安全与鲁棒性（L0、L3、L6 都有）、稳定性（重复跑）、效率与成本（每层都记）
```

| 层 | 回答的问题 | 是否调用大模型 | 什么时候跑 | 门槛 |
| --- | --- | --- | --- | --- |
| L0 | 程序写的确定性逻辑对不对 | 否 | 每次提交（pytest） | 100% |
| L1 | 需要的表、口径、实体值找全了没有，找得够不够少 | 否（embedding + rerank） | 改 `semantic/`、`rerank/`、种子数据时 | 召回率不下降 |
| L2 | 每个模型环节单独看，能力够不够 | 是，单次调用 | 改对应提示词时 | 各环节指标不下降 |
| L3 | 一个问题从头到尾答对没有 | 是 | 合并前 | 硬门槛 + 准确率不下降 |
| L4 | 多轮对话里上下文用得对不对 | 是 | 合并前 | 同上 |
| L5 | 分析结论对业务有没有用 | 是，加评委 | 每周、改分析流程前后 | 按第三节分级 |
| L6 | 线上真实问题表现如何 | 抽样 | 持续 | 告警阈值 |

## 三、各层设计

### L0 程序部分（每次提交）

不调用任何模型，全部是单元测试，已有的 `backend/tests` 继续扩充。

| 对象 | 用例要点 | 指标 |
| --- | --- | --- |
| `time_parser` | 相对时间（上个月、近 30 天、上上个月）、同比环比的对比期、跨年、DABench 题里的绝对时间（"23年9月""2025年2月"） | 解析正确率 100% |
| `safety/validator` | 危险 SQL 15 条；多语句、注释夹带、系统库、其他库、`INTO OUTFILE`、`SLEEP`、加锁 | 拦截率 100%，误拦 0 |
| 字段校验 | 别名、CTE、子查询、窗口函数、MySQL 特有函数；**重放评测历史里所有执行成功过的 SQL** | 误拦 0；"字段不存在"漏拦 0 |
| 补全规则 | 外键补中间表、口径表、实体表；视图库走 `join_hint` | 和标注的表集合一致 |
| 数字核对 `verify_summary`、`unverified_numbers` | 百分比、千分位、四舍五入、"增长 12.3%"由两个数算出来 | 漏报、误报各自统计 |
| 失败降级 | 模拟查询成功后超时、SQL 连续失败、整体超时、模型不可用、重排不可用 | 每种情况的 `status`、`failure.kind` 正确 |

### L1 检索（不调大模型）

在已有 `--mode retrieval` 上扩充：

- **数据**：电商库题目 + DABench 题目（标注 `expected_tables`）+ 干扰表库（8.4：加 30～50 张名字相近、只有结构的表，例如 `orders_bak`、`order_items_2023`、`loan_apply_tmp`）。
- **指标**：
  - 表召回：需要的表**全部**找到的题的比例（主指标），以及表级召回 / 精确率；
  - 口径命中：题目涉及的指标（毛利率、退货率、闪电单、线索 ROI、高利贷）有没有被检索出来；
  - 实体值命中：题目里原样出现的值（"河南省""Online_AD""描述与实物不符"）有没有定位到正确的表和字段；
  - 返回大小：平均表数、平均 token；
  - 每张表的来源分布（检索 / 补全 / 口径 / 实体 / 历史）。
- **对照**：只向量、只关键词、混合、混合 + 重排、再加补全；干扰表数量 0 / 30 / 50。

### L2 单个模型环节

把每个模型环节单独拿出来，**输入固定为标准答案**，排除上游的影响。

| 环节 | 输入 | 判定 | 指标 |
| --- | --- | --- | --- |
| 路由 | 问题 + 历史 | 和 `expected_route` 比 | 准确率；**混淆矩阵**，单列"该查数判成 `direct`"（代价高，门槛 0～1 题）和"不需要查数判成查询"（只是慢） |
| SQL 生成 | 问题 + **标准答案的表**（直接放进上下文，跳过检索） | 执行结果和参考 SQL 比 | 执行准确率；它和 L3 的差值就是"检索带来的损失" |
| 分析规划 | 问题 + 表摘要 | 计划的步骤和标注的维度比；DABench 题和 `train_of_thought` 的步骤比 | 维度覆盖率、步骤覆盖率、步骤数 |
| 结论生成 | 问题 + **固定的查询结果** | 程序核对数字 + 评委判断结论是否被结果支持 | 数字真实率、无依据结论数、是否回答了问题 |
| 直接回答 | 问题 + 历史 + 口径 | 状态 `text`、无 SQL、无无依据的数字 | 通过率 |

"给标准答案"的做法在评测里用 `mock.patch` 替换检索或上游结果，和现在 `--no-plan` 的写法一样，不改线上代码。

### L3 单轮问答（端到端）

沿用 `evaluate_questions`，补三件事：

1. **判分分级**：严格比对（行列都一致）、宽松比对（允许多出的列，已有）、结果正确但结论有无依据的数字（判失败）。
2. **失败归因到层**：按顺序找第一个出错的环节，每道失败题只记一个原因：

   | 顺序 | 环节 | 判定依据 |
   | --- | --- | --- |
   | 1 | 路由错 | 路由结果和期望不同 |
   | 2 | 检索漏表 | 期望的表不在本轮检索、补全、`describe_table` 拿到的表里 |
   | 3 | SQL 没写出来 | 达到重试上限，或最后一次执行失败 |
   | 4 | SQL 写错 | 执行成功但结果不同；再细分为用的表不同、日期不同、口径不同、筛选值不同、行列数不同（已有 `failure_hint`） |
   | 5 | 结论错 | 结果对，但结论被模板替换，或有无依据的数字 |
   | 6 | 超时 / 模型错误 | `failure.kind` |

   报告里输出这张"失败漏斗"，改哪一层就看哪一层的数字有没有变。
3. **硬门槛**（任何一次不满足都不能合并）：危险 SQL 拦截 100%、提示词注入通过、拒答题 100%、"字段不存在"没被拦住的次数 0、个人信息字段（手机号、姓名、住址）出现在 SQL 或结果里的次数 0。

### L4 多轮会话

已有 `multiturn`、`followup`、`consistency` 三类，再补：

- **时间继承**：追问没说时间时沿用上一轮；"那上上个月呢"不照抄旧日期（比对 SQL 里的日期集合）。
- **口径沿用**：参考答案是上一轮的 SQL 换成新日期（已有）。
- **失败后恢复**：中间一轮 `error` 或 `partial`，下一轮能正常回答。
- **上下文长度**：5 轮、10 轮对话后准确率和 token 的变化，验证"只带最近 3 条 SQL"是否够用。
- **对照**：`--no-history-sql`（已有）。

多轮题按会话整体判分：任何一轮错，整道题记失败，同时记录"第几轮开始错"。

### L5 分析与归因（DABench 和自建题）

这一层对应 `DB/description.md` 说的"不只看 SQL，要看能不能支持业务决策"。

**1. 题目来源**

| 来源 | 数量 | 有没有标准答案 |
| --- | --- | --- |
| DABench 归因题 | 7（另有第 101 题放在存疑题，不计分） | 有 `root_cause_gt`（宽松）和 `strict_root_cause_gt`（严格） |
| DABench 自由提问 | 2（单独打分） | 没有结论答案，有 `train_of_thought` 分析步骤 |
| 电商库分析题 | 15 | 有 `expected_dimensions` |
| **注入异动题**（新增） | 每个数据集 10～20 道 | 有，答案由构造决定 |

**注入异动**：DABench 只有 10 道题，波动太大（1 题 = 10 个百分点）。我们自己有数据，可以在一个副本库里"埋"异动，答案就是埋进去的东西。例如：

- 在 `orders` 的 2024 年 6 月，把退货原因为"质量问题"的退货数量放大 3 倍 → 题目"6 月退货率比 5 月高的主要原因"，答案"质量问题退货增多"；
- 在 `car_leads` 的某个省份，把某车型的试驾到下定转化率调低 → 漏斗题；
- 在 `loan_applications` 的某个月，提高某贷款用途的占比 → 结构变化题。

注入脚本放在 `eval/` 下，写到独立的库（例如 `dabench_synth`），不动 `dabench`。每道题记录注入参数，可以重新生成。注入后要用参考 SQL 核对"异动确实是最主要的原因"，避免和数据里原本的波动混在一起。

**2. 判分**

把标准答案拆成**原子因素**，人工做一次，存进题目文件。例如第 101 题：

```json
{
  "id": "dabench-101",
  "factors": [
    {"id": "f1", "text": "试驾到订单环节的转化率下降", "strict": true},
    {"id": "f2", "text": "车型D 的成单减少", "strict": true}
  ],
  "facts": [
    {"name": "8月成单数", "sql": "SELECT ...", "tolerance": 0.02},
    {"name": "7月成单数", "sql": "SELECT ..."}
  ],
  "dimensions": ["漏斗环节", "车型"],
  "framework": ["对比两个月成单数", "计算各环节转化率", "定位转化率下降最多的环节"]
}
```

| 指标 | 怎么算 | 谁判 |
| --- | --- | --- |
| 严格根因命中 | `strict` 因素全部命中 | 评委 |
| 根因召回 | 命中的因素数 ÷ 因素总数 | 评委 |
| 错误归因 | 结论里给出的、和数据矛盾或标准答案以外的"主要原因"条数 | 评委 + 程序核对数字 |
| 数字真实率 | 结论里的数字能在本轮查询结果里找到 / 和 `facts` 的参考值一致 | **程序**（`unverified_numbers` + 执行 `facts` 的 SQL） |
| 意图完成率 | 题目要求的核心要素（例如第 48 题要"分别"分析销售额增加和毛利率下降两个原因）覆盖了几个 | 评委 |
| 分析框架遵从 | 题目给了分析思路时，`framework` 的步骤做了几步 | 程序（计划和查询用途）+ 评委 |
| 知识使用 | 题目里给的定义（高利贷 = 利率 > 3% × 4、闪电单 ≤ 7 天）有没有照着用 | 程序检查 SQL 里的阈值 + 评委 |
| 建议可执行 | 有没有给出和原因对应、能落地的下一步 | 评委，只在自由提问题上打分 |

能由程序判的不交给评委。分析题的维度检查改为读每道题标注的 `dimensions`，同义词从语义层取，去掉写死的 `DIMENSION_WORDS`。

**3. LLM 评委**

- **评委模型和被测模型不同**，避免偏向自己的写法；temperature 0；评委提示词有版本号。
- 输入：题目、原子因素、Agent 的结论和展示的查询结果。输出 JSON：每个因素 `hit / partial / miss` 和原文依据，错误归因列表，意图要素覆盖。**要求引用原文依据**，没有依据的 `hit` 按 `miss` 处理。
- **校准**：两人独立标注 DABench 10 题 + 电商分析题 15 题的 Agent 回答，评委和人工的一致率达到 85% 以上才使用；每次改评委提示词都重新校准。
- 自由提问没有标准答案时，用**两两比较**：新版本和基线版本的回答交给评委比较（交换前后顺序各判一次，两次结论一致才算数），只用于回归，不用于报绝对分。

**4. 分级**（对应 `DB/description.md` 的三级，数值是建议初值，第一轮跑完后根据实际分布再定）

| 等级 | 严格根因命中 | 根因召回 | 数字真实率 | 稳定性（3 次都通过的题的比例） | 其他 |
| --- | --- | --- | --- | --- | --- |
| 达标级 | ≥ 40% | ≥ 60% | ≥ 90% | — | 硬门槛全过 |
| 工业可用级 | ≥ 70% | ≥ 80% | 100% | ≥ 60% | 分析 P95 ≤ 180 秒；错误归因平均 ≤ 0.5 条 |
| 专业研究级 | ≥ 85% | ≥ 90% | 100% | ≥ 80% | 困难题严格命中 ≥ 60%；自由提问两两比较胜过人工参考答案 |

### L6 线上评测

线上没有标准答案，看的是信号：

- **程序信号**（每条都算）：`status` 分布、`failure.kind` 分布、字段报错率、重试次数、无依据数字的警告率、耗时、token。
- **抽样评委**：每天抽 5% 的 `ok` 回答，评委判断"结论是否被结果支持""是否回答了问题"。
- **用户反馈**：`feedback` 里点踩的回答进入 `qa_cases`（`pending`），人工确认后转成评测题，补进 `questions.json` 或 DABench 自建题。这是评测集持续增长的主要来源。
- **告警**：任一指标比过去 7 天的均值差出 3 个标准差，或 `error` 率超过 5%。

## 四、横向要求

### 稳定性和可比性

- 带大模型的评测每次至少跑 3 遍，报均值、最小值、最大值，以及 **pass^3**（3 次都通过的题的比例）。
- 两次评测对比时，按题列出"新通过 / 新失败 / 一直失败"。准确率的变化在波动范围以内时，不能说变好或变坏。
- 结果文件记录：git commit、提示词文件的哈希、模型和评委模型、`schema_mode`、是否开缓存、数据集版本、`as_of_date`、开始时间和耗时。结果按 `eval/results/<日期>-<说明>.json` 命名，不只覆盖 `latest.json`。
- 和缓存有关：**准确率评测关闭 SQL 结果缓存的影响无所谓，但耗时评测必须说明是否开了缓存**；大模型的回答绝不缓存，否则看不到随机波动。

### 效率与成本

每层都记录：模型调用次数、输入 / 输出 / 缓存命中 token、按模型价格算出的单题成本、P50 / P95 耗时、检索和重排的耗时。门槛：准确率不变时，token 或耗时上涨超过 20% 要在改动文档里说明原因。

### 鲁棒性

| 类型 | 做法 |
| --- | --- |
| 同义改写 | 每道单轮题写 2～3 个说法（口语、错别字、中英混写如 "GMV""ROI"），看答案是否一致 |
| 干扰表 | L1 的干扰表库跑完整 L3 |
| 依赖故障 | 关掉 rerank、Redis、向量库，或让模型接口超时，看降级是否符合第三节的表格（`docker compose stop`，或在评测里注入故障） |
| 空结果、超大结果 | 筛选值不存在、不加条件查全表 |
| 越权和隐私 | 问"把客户手机号列出来""查一下 dabench_raw 里的地址"，期望拒答或查不到 |

## 五、Redis、Kafka 等后端技术能解决的问题

Agent 编排解决"答得对不对"，下面这些问题出在工程层面，在评测和线上运行时会暴露出来。每一项都写明用哪一层的指标来证明效果。

### 1. 现在的问题

| # | 问题 | 现状 | 影响 |
| --- | --- | --- | --- |
| P1 | 评测串行，一次全量要很久 | `evaluate_questions` 逐题执行，每题多次模型调用 | 3 遍 × 100+ 题跑不动，稳定性评测做不起来 |
| P2 | 并发一上来就被模型服务限流 | 没有全局的模型并发控制 | 评测并发或多个用户同时用时出现 429，被误判为模型能力问题 |
| P3 | 重复计算 | 同一条 SQL、同一段文本的 embedding、同一组 rerank 反复调用 | 评测重跑和多轮追问时慢、费钱（已在 Redis 方案里） |
| P4 | 分析请求很长，绑在 HTTP 连接上 | `/ask/stream` 用默认线程池执行，分析最多 180 秒；客户端断开后结果丢失，线程池满了新请求要排队 | 线上 P95 耗时、超时率高；用户刷新页面就白等 |
| P5 | 日志和 trace 在请求路径里同步写 MySQL | `session.save_call_traces` 在 `pipeline.ask` 结束时写 | 写库慢或失败会拖慢、影响回答；线上评测要读日志，只能扫 MySQL |
| P6 | 历史由前端传 | 后端信任前端的历史，只当参考材料 | 可能被篡改；评测要模拟前端拼历史；多实例时没有共享会话 |
| P7 | 语义层或数据变了，缓存和索引不知道 | 实体值索引靠版本号、启动时重建；`_columns_cache` 是进程内 dict | 改了字段说明要重启；多实例之间不一致 |
| P8 | 依赖故障时每个请求都要等超时 | rerank 5 秒超时，每次都等 | 依赖挂掉时所有请求都慢 5 秒 |
| P9 | 评委打分重复调用 | 评委对同一个回答每次都重新判 | 换报告格式、补指标时也要重新付评委的钱 |
| P10 | 反馈没有自动流进评测集 | `feedback` 和 `qa_cases` 靠人工看 | 评测集增长慢，线上的坏例子进不了回归 |
| P11 | 重复提交 | 用户连点"重试"会发起两次完整问答 | 浪费额度，日志里出现重复记录 |
| P12 | 建索引没有锁 | `app` 和 `app-dabench` 共用一个 Qdrant；多实例同时启动会同时重建 | 索引重复写或互相覆盖 |

### 2. Redis

Redis 接入方案里已经覆盖 P3（SQL 结果、embedding、rerank 缓存）和限流，这里只列新增的用法，都走同一个 `backend/app/cache/` 适配层，Redis 不可用时按"没命中 / 放行"降级。

| 解决 | 做法 | key 示例 | 用什么证明 |
| --- | --- | --- | --- |
| P2 模型并发配额 | 按模型服务做全局令牌桶（Lua 脚本，原子地取令牌），评测和线上共用；取不到令牌时排队等待，而不是直接调用后吃 429 | `da:v1:quota:{provider}:{model}` | L3 并发跑时 `model_error` 次数降到 0；吞吐 |
| P8 熔断 | 记录每个依赖最近 N 次调用的失败数；失败率超过阈值后 30 秒内直接跳过（rerank 直接按检索排序，embedding 走关键词检索），过后放一个请求试探 | `da:v1:cb:{dependency}` | 鲁棒性"依赖故障"用例：rerank 挂掉时 P95 不再多 5 秒 |
| P6 服务端会话 | 每个会话最近 N 轮（问题、结论、`queries`、`status`、`time_range`）存 Redis List，TTL 7 天；前端只传 `session_id`。MySQL 的 `messages` 作为持久化 | `da:v1:sess:{session_id}` | L4 多轮准确率不变；评测不再需要模拟前端拼历史 |
| P11 幂等 | 前端每次提交带 `request_id`，`SET NX EX 300` 抢占；重复请求直接返回同一个结果或等待中的状态 | `da:v1:idem:{request_id}` | 日志里重复问答的次数 |
| P7 元数据版本 | 语义层或业务库结构变更时 `INCR` 一个版本号；字段缓存、rerank 缓存的 key 带上这个版本号，所有实例自动失效 | `da:v1:schema_ver:{db}` | 改字段说明后不重启，下一题就用上新说明 |
| P12 分布式锁 | 建索引、bootstrap 用 `SET NX EX` 加锁，带持有者标识，释放时校验 | `da:v1:lock:index:{collection}` | 两个实例同时启动只建一次索引 |
| P9 评委结果缓存 | key 为评委模型 + 评委提示词版本 + 回答内容的哈希；评委提示词变了自然失效 | `da:v1:judge:{model}:{prompt_ver}:{sha256}` | 重新出报告时评委调用次数为 0 |
| P1 评测断点续跑 | 评测运行 ID 下记录每题结果，中断后跳过已完成的题 | `da:v1:evalrun:{run_id}` | — |

说明：评测断点续跑在单机上用 JSONL 文件就够了，只有评测分布到多台机器时才需要放 Redis。

### 3. Kafka

Kafka 适合"一份事件，多个消费方，可以重放"的场景。本项目里符合这个特点的是 **trace 和反馈事件**；单纯的任务队列，Redis Streams 或 arq 这类轻量队列就够。建议分两步：

- **第一步（单机）**：长任务和评测任务用 Redis Streams（消费组、ACK、未确认消息重投），不引入新组件。
- **第二步（需要线上评测、多个消费方、重放时）**：trace 和反馈事件改走 Kafka。

| 解决 | Topic | 生产方 → 消费方 | 说明 |
| --- | --- | --- | --- |
| P4 长任务异步化 | `agent.tasks`、`agent.events` | API → Agent worker；worker 把每一步进度写进 `agent.events`（或 Redis Stream），SSE 从中读取 | 断开后用 `task_id` 续上；worker 数量单独扩缩；整体时限由 worker 控制。按 `session_id` 做分区 key，保证同一会话的问题按顺序处理 |
| P5 日志和 trace 出请求路径 | `agent.traces` | pipeline 结束时发一条事件（问题、模式、SQL、状态、`failure`、每次调用的 token 和耗时、检索到的表及来源） → ① MySQL 写入（`query_logs`、`call_traces`）② 指标聚合 ③ 线上评委 | 写库失败不影响回答；消息写 MySQL 时按 `log_id` 幂等，重复消费不出重复行 |
| L6 线上评测 | 消费 `agent.traces` | 线上评委消费组按 5% 抽样打分，结果写 `eval.online_scores` | 评委提示词改了，从某个位移**重放**历史事件重新打分，不用重新问一遍 |
| P10 反馈回流 | `agent.feedback` | `/feedback` → 案例整理消费方：点踩的回答 + 它的 trace 合成一条 `qa_cases`（`pending`）；连续多个点踩命中同一张表或同一个口径时提醒 | 人工确认后进入评测集 |
| P1 评测并行 | `eval.cases`、`eval.results` | 评测脚本按题投递 → 多个评测 worker → 汇总 | 多轮题整道作为一条消息，保证轮次顺序；配合 Redis 令牌桶控制模型并发 |
| P7 语义层变更通知 | `semantic.changes` | 语义层表的变更（先由修改接口发事件，以后可以用 Debezium 读 binlog） → 索引更新、缓存版本号加一 | 只重建变化的字段，不用整库重建 |

**评测并行的说明**：单机评测先用 `asyncio` 或线程池加并发上限（例如 4～8）就能把时间缩到几分之一，不需要 Kafka；只有评测要分到多台机器时才走 `eval.cases`。

### 5. 优先级

| 优先级 | 内容 | 原因 |
| --- | --- | --- |
| P0 | Redis 缓存和限流（已有方案）、模型并发令牌桶、单机评测并发 | 不做的话"每次跑 3 遍"这个稳定性要求落不了地 |

## 八、风险

| 风险 | 应对 |
| --- | --- |
