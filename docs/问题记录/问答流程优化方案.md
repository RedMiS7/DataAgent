# 问答流程优化方案：从用户输入到生成回复

日期：2026-11-08，2026-11-09 更新

状态：第 0 到 7 步、8.1 和 8.2 已完成，8.3 和 8.4（模型按问题检索表、大库验证）待实施，表结构裁剪由以后的评测决定。各步的改动记录见第七节。

## 结论

这次优化有五个目标：

1. **多轮对话带上之前的 SQL**：每轮回答除了结论，还把这一轮的查询用途和 SQL 一起交给模型。不传查询结果的数据行。（已完成）
2. **不需要查数的问题正常回答**：解释口径、解释上一轮结论、闲聊，不报错。（已完成）
3. **出错时用户也能拿到有用的信息**：超时、查询次数用完、SQL 一直写不对时，展示已经查到的结果、系统是怎么理解问题的、失败原因和下一步建议。（已完成）
4. **"字段不存在"一定能拦住**：执行前对照数据库的真实字段校验，报错时直接给出正确候选。（已完成）
5. **模型按问题检索，只拿需要的表**：模型决定要不要检索、检索什么；程序负责混合检索、重排、补全关联的表，并把检索到的表的全部字段交给模型。（检索 8.2 已完成，接入问答 8.3 待实施）

另外，**表内要不要按字段裁剪，由评测结果决定**，见第五节。

整体原则：

- **模型决定"要不要查、查什么"，程序负责"查全、查对"**：时间解析、检索、补全关联的表、表和字段校验、数字核对都由程序做，结果是确定的。
- **模型负责理解问题、写 SQL、写结论**，缺什么可以调用工具再查。
- **检查只认元数据，不写死表名**：表、字段、外键、指标、实体字段都从数据库和语义层读。换库时改数据，不改代码。
- **"字段不存在"由程序兜底，必须拦住**；**"字段存在但用错了"只能降低概率**，所以要让依据可见，并持续评测。
- **失败也是一种回答**：能给多少就给多少，并说清楚缺了什么。

## 一、流程

标注：**已完成**是第 0 到 7 步已经做完的；**8.1 到 8.4** 是第 8 步里还没做的阶段，见第七节。

```
用户问题 + 历史（问题、结论、每轮的查询用途和 SQL；失败的轮次也有回答）
  ① 程序：整理历史                                          已完成
  ② 程序：解析时间、拦截敏感问题                              已完成
  ③ 程序：预先检索指标口径、案例、实体值；放入上一轮 SQL 用到的表    8.3
  ④ 程序：组装提示词                                        8.3
  ⑤ 模型：路由（查询 / 分析 / 直接回答）                       已完成
  ⑥ 模型：判断要不要检索表，调用 search_semantic               8.3
  ⑦ 程序：混合检索 → 按表汇总 → 重排 → 补全                    已完成（8.2）
  ⑧ 模型：生成 SQL；不需要查数时直接回答                       已完成
  ⑨ 程序：校验（安全、表、字段），失败带修正信息打回               已完成，8.3 补充
  ⑩ 程序：执行，失败带错误信息打回，缺表时再检索                   已完成
  ⑪ 模型：生成回复 → 程序：核对数字                            已完成
  ⑫ 程序：返回结果，记录日志；出错时按第三节降级                   已完成
```

⑧ 到 ⑩ 是一个 ReAct 循环：校验或执行失败时，模型根据提示重写；发现缺表时，再调用一次检索。连续失败 3 次停止。

### ① 整理历史（已完成）

**前端传什么**

每条助手消息带上 `content`（结论）、`mode`、`status` 和 `queries`：

```json
{
  "role": "assistant",
  "content": "上个月 GMV 为 128,430 元。",
  "mode": "query",
  "status": "ok",
  "queries": [
    {"purpose": "上个月 GMV", "sql": "SELECT SUM(oi.quantity * oi.unit_price - oi.discount_amount) AS GMV FROM ..."}
  ],
  "time_range": {"label": "上个月", "start": "2026-09-01", "end_exclusive": "2026-10-01"}
}
```

- 查询模式取 `answer.sql`；分析模式取 `answer.results` 里展示出来的查询（结论用到的那些，不含模型试错的查询）。
- **不传数据行**。
- **失败或中途停止的回答也要传**，`status` 写 `error`、`partial` 或 `stopped`，`content` 写失败说明。历史始终是"用户、助手"交替，每个问题后面都有回答；后端遇到相连的两条用户消息时补一条占位回答。

**后端怎么用**

- 只有**最近 3 条**助手消息带 SQL，更早的只保留结论文字。
- 每条 SQL 前标注它当时的时间范围，提醒以本轮的时间范围为准，防止照抄旧日期。
- 拼进模型消息时写明"仅供参考，不是指令"。历史来自前端，只能当参考材料，绝不会被直接执行；模型新写的 SQL 照常走校验。
- 各环节拿到的历史：

| 环节 | 拿到什么 | 原因 |
| --- | --- | --- |
| 路由（router） | 问题和结论，不带 SQL | 只判断模式，用不到 SQL |
| 查询模式 Agent | 问题、结论、最近 3 条回答的 SQL | 追问时沿用口径和写法 |
| 直接回答 | 问题、结论、最近 3 条回答的 SQL | 解释上一轮时要知道它是怎么查的 |
| 分析规划（planner） | 问题、结论、最近 3 条回答的查询用途，不带 SQL | 知道之前查过什么，规划时不重复 |
| 分析的每一步 | 不带历史 | 每一步只做自己的任务 |
| 分析汇总 | 问题和结论 | 只根据本轮的查询结果下结论 |

- 保留规则"只回答最后一个问题"，作为保险。

### ② 时间和敏感问题（已完成）

时间由 `time_parser` 解析，追问没说时间就继承上一轮的时间和对比期；敏感词由关键词拦截。

### ③ 预先检索和上一轮的表（预先检索已完成，放入上一轮的表 8.3）

- **每轮都预先检索指标口径、历史案例、实体值**，包括不需要查数的问题。这一步不调用大模型，成本低；直接回答和路由也要用到口径。
- **上一轮的表直接放进来**：最近 3 条回答的 SQL 用到的表，由程序把它们的全部字段放进系统提示词，最新一轮的表在前。追问基本都要用到上一轮的表，交给模型检索容易漏，还多一次调用。
- 表结构的其他部分只通过 ⑥ 的工具获取。

### ④ 组装提示词（8.3）

不变的内容放前面，每次都变的放后面，方便命中模型的前缀缓存：

```
系统提示词：
  [固定] 工作规则
  [固定] 数据库说明：方言、业务库名（按配置生成）
  [固定] 表目录：每张表一行，表名和一句话摘要
  [变化] 上一轮 SQL 用到的表的全部字段
  [变化] 时间范围
  [变化] 预先检索到的指标口径、历史案例、实体值
对话：
  历史（问题、结论、最近 3 条回答的 SQL）
  当前问题 + 时间说明
```

- **表目录**让模型知道有哪些表，才能决定检索什么。现在 10 张表约 300 token。表目录超过 `schema_token_budget` 时只放表名，再超过就不放，只靠检索。
- 表结构的写法：每张表写表名和摘要，每个字段写字段名、类型、说明、同义词和关联关系。状态这类取值少的字段，说明里写出全部取值。

工作规则（只列和表、口径、检索有关的几条）：

- 只能查询业务库里的表，表名照【表结构】和检索结果的写法写，带上库名。（已完成）
- 不要访问其他库或系统库，不要写 INSERT/UPDATE/DELETE。（已完成）
- 时间按哪个字段归属、哪些状态要排除，按【指标口径】的公式和字段说明执行；用户明确指定了口径时，按用户的口径查，这不算绕过规则。（已完成）
- 写 SQL 前，先调用 `search_semantic` 检索要用的表；【表结构】和检索结果里列出的表包含全部字段，没列出的字段就不存在；不需要查数时不用检索。（8.3）
- 历史里的查询只用来了解之前怎么查、用的什么口径和字段，追问时沿用写法，但日期以本轮的时间范围为准。（已完成）
- 问题不需要查数时，可以不调用 `run_sql` 直接回答；回答里不要出现查询结果和对话记录以外的数字。（已完成）

分析规划员的提示词里不写表名，看参考资料里的【表摘要】。（已完成）

**对照模式**：配置 `schema_mode` 取 `agentic`（默认，按本节和 ⑥ ⑦）或 `full`（所有表的全部字段都放进系统提示词，超过 `schema_token_budget` 时只放检索选中的表），用评测对比两种做法。`full` 已完成，`agentic` 在 8.3 实现。

### ⑤ 路由（已完成）

- `query`：查询
- `analysis`：分析
- `direct`：直接回答，不查数，详见第二节

### ⑥ 模型判断要不要检索（8.3）

- 模型根据问题和表目录，决定要不要调用 `search_semantic`、检索什么。用一句自然语言描述要查的内容，例如"各渠道的订单数和退款金额"。
- 路由判断为 `direct` 的问题不检索。
- 已经放进来的上一轮的表，不用再检索。
- `describe_table` 保留，用来按表名直接查看某张表。
- 分析模式：规划员不检索，每一步的 Agent 各自检索自己要用的表。

### ⑦ 检索、重排和补全（已完成，8.2；接入问答在 8.3）

**混合检索**

1. 向量检索：用字段、指标、案例、实体值的索引。
2. 关键词检索：表名、字段名、具体取值（"直播带货""顺丰"）靠它补，每次都和向量检索一起跑。
3. 两路结果按排名用 RRF 合并。
4. **按表汇总**：命中的字段归到所在的表，表的分数取命中字段的最高分，再加上表摘要的匹配分。取前 `rerank_candidates` 张（默认 20，不足时全部）作为候选。

**重排（每次检索都做）**

- 用专门的重排模型给候选表打分，不调用大模型。默认用阿里云百炼的 `qwen3.7-text-rerank`（原生接口 `https://dashscope.aliyuncs.com/api/v1/services/rerank/text-rerank/text-rerank`），和 embedding 用同一个 key。`qwen3-rerank` 也能用，通过 `RERANK_MODEL` 切换。
- 每张候选表写成一段文本：表名、摘要、字段名和字段说明。查询是模型调用 `search_semantic` 时写的那句检索描述。
- 按重排分数取前 `search_top_tables` 张（默认 5），再进入补全。补全放在重排之后，补上的中间表、口径表、实体表不会被重排去掉。
- 通过适配层访问（新增 `backend/app/rerank/`），测试用假的重排模型。
- 没有配置、调用失败或超时（`rerank_timeout_seconds`，默认 5 秒）时，按检索的排序继续，记日志，检索结果里注明"重排不可用"。

**补全：程序检查表够不够**

| 检查 | 依据 | 来源 |
| --- | --- | --- |
| 关联的中间表 | 外键：选了 orders 和 categories，补上 order_items 和 products | 先读数据库声明的外键（`information_schema.KEY_COLUMN_USAGE`）；读不到时用语义层的 `join_hint`。走视图的库（例如现在的 `safe`）视图上没有外键，只读账号也看不到底层表，用 `join_hint` |
| 口径用到的表 | 命中指标的 `related_tables` | 语义层的指标数据 |
| 实体值所在的表 | 问题里的"直播带货"属于 `channels.name`；只认问题里原样出现的值，向量找到的相近值不补表 | 语义层的实体字段标记 `is_entity` |
| 外键字段指向的表 | 问"各渠道"命中了 `orders.channel_id`，补上 `channels`；命中 `refunds.product_id`，补上 `products` | 和关联的中间表用同一张关联图 |

- 关联图由外键和 `join_hint` 合并而成，沿最短路径补中间表。
- 实体值：程序对打了 `is_entity` 标记的字段统一执行 `SELECT DISTINCT 字段 FROM 表`（限制条数），实体值的索引里记下它属于哪张表、哪个字段。现在的商品名、类目、渠道、省份四个字段打上标记。实体值的索引带版本号，版本变了启动时自动重建。
- 补全只加表，不删表。

**返回给模型**

- 选中的表，每张表的全部字段，写法和【表结构】一样；
- 命中的指标口径、历史案例、实体值（注明在哪张表的哪个字段）；
- 每张表被选中的原因：检索命中、关联补全、口径需要、实体所在。

返回的表结构总量不超过 `schema_token_budget`，超出时按得分截断，补上的中间表优先保留，并注明还有哪些表没放。

### ⑧ 生成 SQL（已完成）

模型判断不需要查数、直接给出文字回答时，状态记为 `text`，按第二节处理。

### ⑨ 校验：安全、表和字段

- **安全检查**（已完成）：只允许单条只读查询；拦截危险函数、加锁、导出文件；系统库和其他库一律拦截。
- **表白名单**（已完成）：业务库名来自配置，可查的表是只读账号在业务库里能看到的表，方言来自 `sql_dialect`。读不到表和字段时只检查库名，由只读账号的权限兜底。
- **字段校验**（已完成）：用 sqlglot 的 `qualify(..., validate_qualify_columns=True)` 对照数据库的真实字段检查每个字段。只拦"字段不存在"，其他解析失败一律放行，**宁可放过，不误拦合法 SQL**。报错时直接给出修正信息：

  ```
  字段不存在：ad_daily_stats.cost。最接近的字段：spend。
  ad_daily_stats 的字段：id, campaign_id, stat_date, impressions, clicks, spend, attributed_gmv, attributed_orders
  ```

  字段写在子查询或 CTE 的别名上（例如 `cur.gmv`）时，提示写出这个子查询的列，例如"子查询 cur 里没有 gmv，它的列有：pid, refund_amt"。（8.3）
- **表必须检索过**（8.3）：SQL 用到的表必须是这一轮检索过、`describe_table` 查过、或程序放进来的表。否则打回，提示"表 X 还没有检索过，先调用 search_semantic 或 describe_table"，计入连续失败次数。

### ⑩ 执行（已完成）

- 数据库报 1054 时，和 ⑨ 一样附上那张表的真实字段和最接近的字段名。
- **重试上限**：同一个 Agent 连续失败（校验或执行）达到 `sql_max_retry`（3）次后，`run_sql` 返回"不要再试，如实告诉用户没查出来"，之后按第三节降级。成功执行一次就清零。
- 模型发现缺表时，可以再调用一次 `search_semantic`。

### ⑪ 生成回复（已完成）

- 查询模式的结论要通过 `verify_summary`，不通过就改用模板结论；分析模式用 `unverified_numbers` 找出没核对上的数字，作为警告展示。
- 历史里不传数据行，结论里的数字只会来自本轮的查询结果。直接回答的数字核对见第二节。

### ⑫ 返回和日志（已完成）

- 返回结构带上第二、三节的状态和 `failure` 字段；前端把这一轮的 SQL 存进会话，下一轮由 `buildHistory` 带上。
- 每次模型调用记录 token 和其中命中缓存的 token；评测统计缓存命中率。
- 日志记录放进上下文的表和是否完整、字段校验拦截、失败类型。8.3 再记录每张表的来源（检索 / 补全 / 口径 / 实体 / 历史）、检索次数和重排是否可用。

## 二、不需要查数的问题（已完成）

| 类型 | 例子 | 需要什么 |
| --- | --- | --- |
| 解释口径 | "GMV 包不包括运费？" | 指标口径（检索） |
| 解释上一轮 | "刚才为什么说渠道 A 拖了后腿？" | 历史结论和历史 SQL |
| 改写上一轮 | "把上面的结论写成一段话发给老板" | 历史结论 |
| 能力范围、闲聊 | "你能查什么？""你好" | 表摘要 |

**1. 路由 `direct`**

- 拿不准时偏向查数（`query` 或 `analysis`）：不需要查数却去查了，只是慢一点；需要查数却直接回答，用户拿不到数据。
- 走 `direct` 时，用一个不带工具的 Agent 回答，输入是历史、检索到的口径和表摘要。它发现其实要查数时输出"【需要查数】"，转为查询模式。

**2. 查询和分析模式下的文字回答**

- 模型给出了文字回答、没有任何查询：返回这段文字，状态记为 `text`。
- 模型既没有回答，也没有查询：按第三节"没有任何结果"处理。

**3. 数字核对**

直接回答里的数字只能来自历史结论、检索到的口径说明或用户的问题，历史 SQL 里的数字（`LIMIT`、日期）不算依据。其他数字作为警告展示："这些数字没有查询依据：……"。

**4. 前端**

`text` 状态的回答卡片只显示文字结论，不显示表格、图表和 SQL 标签页。

## 三、出错时也给用户有用的信息（已完成）

### 原则

- **后端总是返回完整的回答卡片**（`answer` 事件），带上状态和失败说明。`error` 事件只留给传输层的问题：网络断开、服务崩溃、返回的数据无法解析。
- **能给多少就给多少**：已经查到的结果要展示，系统怎么理解问题的要展示，尝试过的 SQL 要能看到。
- **说清楚缺了什么、为什么、接下来可以怎么做**。

### 状态和失败说明

| 状态 | 含义 |
| --- | --- |
| `ok` | 正常 |
| `empty` | 查询成功，没有数据 |
| `refused` | 涉及隐私或不该执行的请求 |
| `text` | 不需要查数，直接回答（第二节） |
| `partial` | 有一部分查询成功了，但没能完整回答 |
| `error` | 没有拿到任何查询结果 |

有失败时填写 `failure`：

```json
{
  "kind": "timeout",
  "message": "模型生成结论时超时，下面是已经查到的结果。",
  "suggestion": "可以稍后重试，或者把问题拆小一点。"
}
```

`kind` 的取值：`timeout`（超时）、`sql_failed`（SQL 一直写不对）、`model_error`（模型服务出错）、`no_answer`（模型没有给出任何回答）、`step_failed`（分析有步骤没查到数据）、`unexpected`（其他异常，例如代码问题）。

### 每种情况给用户什么

| 情况 | 给用户什么 |
| --- | --- |
| 模型没调用 `run_sql`，但给出了文字回答 | `text`，按第二节处理 |
| SQL 连续失败达到上限 | `error` + 回答卡片：时间范围、用到的表、相关口径、最后一次尝试的 SQL、用大白话说的失败原因、建议换个说法 |
| Agent 出错（模型超时、调用失败），**已经有查询成功** | `partial`：展示已有的查询结果，结论用模板生成，说明"模型生成结论时出错，下面是已经查到的数据" |
| Agent 出错，**还没有查询成功** | `error` + 回答卡片：时间范围、用到的表、相关口径、失败原因、建议 |
| 整体超时 | 到时间后停止。有结果按 `partial`，没有按 `error` + 回答卡片 |
| 分析模式查询次数用完 | 模型基于已有结果作答；结论下方注明"查询次数已用完，分析基于以下 N 条查询" |
| 分析模式某一步失败 | 汇总时说明缺了哪部分，计划里标出失败的步骤，状态记为 `partial` |
| 分析汇总超时 | 改用模板结论，卡片上注明"结论由模板生成" |
| ReAct 轮数用完 | 有查询结果按正常处理；没有查询按第二节的 `text` 或 `error` 处理 |
| 模型服务不可用（没配置、key 错、网络不通） | `error` + 回答卡片，`kind` 为 `model_error`，说明是模型服务的问题，提示到设置页检查 |
| 查询结果为空 | `empty`，说明查询条件（时间范围、筛选值），方便用户调整 |

### 时限

- 单次模型调用的超时：`llm_timeout_seconds`，传给模型客户端。
- 整体时限：查询模式 `ask_timeout_seconds` 120 秒，分析模式 `analysis_timeout_seconds` 180 秒。到时间后取消 Agent，按上表处理已有结果。
- 单次模型调用的输出上限：`llm_max_tokens` 8192，避免长 SQL 被截断。

### 前端

- `AnswerCard` 根据状态显示：`partial` 显示黄色提示条加已有的结果；`error` 显示失败原因、建议，以及"我是怎么理解这个问题的"（时间范围、用到的表、口径），尝试过的 SQL 放在 SQL 标签页。
- 卡片上提供"重试"和"用分析模式重新回答"。
- `useChat.ts` 里的 `error` 事件只用于传输层的失败。

## 四、检索召回率评测（8.1）

链路最怕的是检索漏表，所以先把检索本身量出来，再改链路。

- 从 `eval/questions.json` 里有参考 SQL 的题（71 题里有 39 题），用 sqlglot 从参考 SQL 抽出"应该用到的表"。没有参考 SQL 的分析题（15 题），手工标注 `expected_tables`。
- 新增 `--mode retrieval`，对每道题跑检索（不调用大模型，只调用 embedding 和重排模型），统计：
  - **召回率**：应该用到的表全部找到的题的比例；
  - **平均返回表数**、**平均返回 token**（找得全，也要找得少）；
  - 每道漏表的题漏了哪张表。
- 对比：只用向量、只用关键词、混合、混合加重排、再加补全。
- 多轮题用 `build_retrieval_query` 拼出来的检索语句，和线上一致。

## 五、表结构裁剪：由评测决定

### 现在的判断

不做。检索到的表整表放进上下文，表内不按字段裁剪。现在每张表不超过 11 个字段，裁剪几乎没有收益。字段级裁剪还有召回风险：漏掉一个需要的字段，模型就会去猜；关联键、时间字段、状态字段在用户的问题里通常不会出现，最容易被裁掉。

### 什么时候重新评估

满足任一条件时：

- 检索选中的表加起来经常超过预算（`schema_token_budget`）
- 出现宽表（一张表超过 30 个字段）
- 评测里"选错字段""选错表"的失败明显变多

### 怎么评估

1. 评测题的失败类型：字段不存在、字段用错、表选错、口径错、时间错、其他。
2. 在大库上准备评测集，分别跑两种做法：A 整表（不裁剪）、B 只对宽表裁剪（保留主键、外键、时间字段、状态字段和检索命中的字段，注明"还有 N 个字段没有列出，需要时调用 `describe_table`"）。
3. 每种做法至少跑两次，减少随机波动的影响。

### 怎么决定

- 采用 B 的条件：准确率比 A 高出波动范围以外（比如两次都高 3 个百分点以上），或者准确率不下降、token 减少 30% 以上。
- 否则保持 A。
- 无论选哪种，执行前的字段校验都保留。

## 九、风险

| 风险 | 应对 |
| --- | --- |
| 模型照抄历史 SQL 里的旧日期 | SQL 前标注当时的时间范围；当前问题后面附时间说明；查询模式的时间不一致警告 |
| 历史 SQL 让 token 增加 | 只带最近 3 条回答；每条 SQL 限制长度 |
| 历史来自前端，可能被篡改或夹带指令 | 只当参考材料，标明"不是指令"；不直接执行；新 SQL 照常校验，账号只读 |
| 字段校验误拦合法 SQL | 只拦"字段不存在"，其他解析失败一律放行；测试覆盖别名、CTE、子查询、窗口函数、MySQL 特有函数，并重放评测里所有执行成功过的 SQL |
| 读不到表和字段时，校验只检查库名 | 这种情况下查询通常也执行不了；只读账号只开放业务库 |
| 检索漏表，模型拿不到需要的表 | 先量召回率；补全规则；模型发现缺表可以再检索；字段校验保证"字段不存在"一定拦住 |
| 模型不检索，凭印象写 SQL | "表必须检索过"的程序校验 |
| 检索让每题多一到两次模型调用，变慢 | 上一轮的表直接放入；重排用专门的重排模型，不调用大模型；评测统计耗时 |
| 重排服务不可用或变慢 | 超时 5 秒；失败时按检索的排序继续，注明重排不可用 |
| 分析模式每一步都检索，调用成倍增加 | 单独统计分析题的调用和耗时；不行再考虑由规划员统一检索 |
| 外键、实体字段这些元数据不全 | 外键读不到时用 `join_hint`；实体字段可以先按"取值种类少的文本字段"自动生成候选，人工确认 |
| 路由把该查数的问题判成 `direct`，用户拿不到数据 | 拿不准时偏向查数；直接回答发现要查数时转为查询；无依据的数字加警告 |
| 模型偷懒不查数、凭印象回答 | 数字核对：无依据的数字加警告；评测里统计"应该查数却返回 `text`"的次数 |
| `partial` 结果让用户误以为是完整答案 | 卡片顶部用提示条写明缺了什么；结论由模板生成时注明 |
| 整体时限设得太短，正常的分析被截断 | 时限作为配置项，按评测里的最长耗时加余量设定 |
| 这个方案解决不了"字段存在但用错了" | 靠指标口径、字段说明、历史 SQL 和评测；以后再考虑多候选、一致性核对和澄清反问 |
