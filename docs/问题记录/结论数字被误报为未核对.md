# 结论数字被误报为未核对

日期：2026-11-07

状态：已修复。核对范围改为本次回答的全部查询；结论用到未引用查询里的数字时，那条查询也会显示出来。

## 现象

分析模式改为先规划再执行后，用 15 道分析题评测，计划流程有 5 题提示“这些数字未能在查询结果中核对”。被标出的数字有：

| 题目 | 被标出的数字 |
| --- | --- |
| 最近生意怎么样？ | 45、209 |
| 上个月GMV为什么比上上个月低？ | 19 |
| 最近30天广告投放效果怎么样，钱花得值吗？ | 292、71 |
| 本月退款为什么变多了？ | 185 |
| 上个月客单价为什么下降了？ | 8.20 |

结论里对应的写法是“文具45号”“宠物209号”“鞋靴292号”“手机配件热销款185号”这类商品名，以及“20 个类目中 19 个上升”这类个数。

## 原因

`unverified_numbers` 只拿结论引用到的那几条查询的结果做核对。

结论里经常有两种写法：

- 一条要点写错了引用编号，比如数字来自查询 2，却标成了 [查询10]。
- “建议”这一行不写引用，却提到了别的查询查出的商品或数字。

这些数字确实在查询结果里，只是不在被引用的那几条里，于是被当成来历不明的数字。

商品名里的编号本身没有问题：核对时会从结果的文字格子里取出数字，`鞋靴热销款292号` 里的 292 能核对上，前提是这一行在参加核对的查询里。

“19 个”是模型自己数出来的个数，查询结果里确实没有，标出来是对的，不算误报。

## 排查过程

1. 一开始看到被标出的大多是商品编号，判断成“核对把商品编号当成了数字”。这个判断是错的。
2. 读 `answer.py` 发现，`_row_numbers` 已经会从商品名这类文字里取出数字。
3. 用同一句结论“建议：加投 ROI 2.78 的鞋靴292号”直接测试 `unverified_numbers`：

   | 参加核对的查询结果 | 被标出的数字 |
   | --- | --- |
   | 含 `鞋靴热销款292号, 2.78` | 无 |
   | 只含 `社交种草, 2.78` | 292 |

4. 用真实模型重跑分析题，逐个查被标出的数字出现在哪条查询里。复现到一次：结论写“图书 -3.2% [查询10]”，3.2% 实际出现在查询 2，而查询 2 没有被引用。

教训：看到误报先读核对代码、用最小例子复现，再下结论，不要只凭被标出的数字长什么样来猜原因。

## 方案选择

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| “数字+号”一律当编号，不核对 | 不用 | 模型编出不存在的商品（如“鞋靴999号”）也查不出来 |
| 核对范围改为本次回答的全部查询 | 采用 | 消除引用写错、漏写造成的误报，编造的数字照样能查出 |
| 数字来自未引用的查询时，把那条查询也显示出来 | 采用 | 用户能看到数字的出处 |
| 计数类数字（如“19 个”）放行 | 不做 | 个数确实不在查询结果里，放行后会漏掉数错的情况 |

## 修复

- `pipeline.py` 的 `_finish_analysis`：数字核对改用本次回答的全部查询结果。
- 新增 `_uncited_sources`：先用被引用的查询核对，找出核对不上的数字，再看哪些未引用的查询含有这些数字，把它们加入答案中显示的查询。
- 测试：`test_pipeline.py` 新增“未引用查询里的商品能通过核对并显示”和“没有任何查询返回的商品仍被标出”；`test_planner.py` 新增计划流程中的同类测试。

## 修复后仍会提示的情况

以下数字不在任何查询结果里，修复后仍会提示，这是预期行为：

- 模型自己算的差值或比例。比如结论写“不喜欢”退款增加 24,237.96 元，这是 73,200.48 − 48,962.52 心算出来的。数是对的，但违反了“比例、差值写进 SQL 算”的规则。
- 模型自己数的个数，比如“19 个类目上升”。
