# 失败的轮次也传回答

日期：2026-11-08

## 做了什么

这是[问答流程优化方案](../问题记录/问答流程优化方案.md)的第 2 步。

前端：

- `frontend/src/lib/conversations.ts`：`buildHistory` 不再丢掉失败和中途停止的回答，每个问题后面都跟一条回答。
  - 完成的回答：内容是结论；没有结论时（失败的回答）用失败原因。同时带上 `status`（`ok`、`partial`、`error` 等）。
  - 请求本身出错（网络、服务异常）：内容是错误信息，`status` 为 `error`。
  - 中途停止：内容为空，`status` 为 `stopped`。
  - 正在生成的回答不发送。每条内容截到后端允许的 4000 字。
- `frontend/src/types.ts`：`HistoryMessage` 新增 `status`。

后端：

- `backend/app/api/schemas.py`：`HistoryMessage` 新增 `status`，可选值是回答的各种状态再加 `stopped`。
- `backend/app/agent/answer.py`
  - 新增 `history_content`：把历史回答整理成模型看到的文字。失败的回答写成"（这一轮没有查到结果：原因）"，停止的回答写成"（用户中途停止了这一轮，没有回答）"，其他回答照旧去掉 `[查询N]` 引用标记。
  - 新增 `fill_missing_replies`：兜底。两条用户消息挨在一起、或历史以用户消息结尾时，补一条"（这一轮没有得到回答）"。旧版前端、或别的客户端发来的历史也不会再出现"没回答的问题"。
- `backend/app/agent/pipeline.py`：问答开始时先补齐回答，路由、规划和 Agent 用的都是补齐后的历史；补了占位回答时写一条日志。`history_pairs` 改用 `history_content`。
- `backend/app/agent/router.py`：路由看到的历史也用 `history_content`，能看出上一轮失败了。

测试和评测：

- `backend/tests/test_pipeline.py`：新增 3 个测试（只有问题没有回答时补占位、连续问题各补一条、失败和停止的回答怎么写）。原来"30 条历史都交给模型"的测试用的是 30 条连续的用户消息，现在会被补上占位回答，改成了用户和助手交替的 30 条，测试的目的（历史不截断）不变。
- `backend/tests/test_router.py`：新增 1 个测试，路由输入里能看出上一轮失败。
- `frontend/src/lib/__tests__/conversations.test.ts`：原来"丢掉失败和停止的回答"的测试改为"保留"，新增 3 个测试（失败原因和状态、正在生成的不发送、长度截断）。
- `eval/runner.py`：`reply_history` 按新的前端规则生成历史，失败的回答也会发送。
- `eval/questions.json`：新增 t06，历史里是新前端发送的"失败回答 + 原因"。原来的 t04 保留，它模拟旧前端只发问题、不发回答，用来检查后端的兜底。

## 为什么做

第 0 步的基线里，t04 复现了这个问题：上一轮失败后，前端只发了用户问题、没有回答，模型看到一个"没回答的问题"，就去回答了上一轮的"各省份退款金额"，没有回答这一轮的"订单数"。11-05 修过的追问答错也是同一类原因。

## 有什么用

- 上一轮失败或被停止后，接着问的问题不会被上一轮带偏。
- 模型知道上一轮失败了、为什么失败，用户说"那换个说法"之类的话时有上下文。
- 后端自己补齐历史，不依赖前端一定发对。
