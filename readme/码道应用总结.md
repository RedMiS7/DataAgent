# 码道在项目开发中的应用总结

## 1. 使用概况

| 项 | 内容 |
| --- | --- |
| 工具 | 华为云码道（CodeArts） |
| 使用阶段 | 架构设计、后端开发、前端开发、测试与评测、缺陷排查、文档撰写 |
| 参与范围 | 待填（按实际统计：涉及模块数 / 生成代码占比） |
| 材料出处 | `codearts_proof/01_prompt`、`02_generate`、`03_refactor`、`04_debug` |

## 2. 典型应用场景

### 2.1 架构设计与方案对齐
- 用码道梳理五步问答主流程的状态与异常分支，确定“报错回灌、最多重试 3 次”的实现边界。
- 讨论语义层四个向量集合（schema_items / metrics / qa_cases / entity_values）的职责划分，避免检索内容互相污染。
- 产出：流程伪代码与接口草案，人工评审后定稿。

### 2.2 代码生成
- 生成 FastAPI 路由、SQLAlchemy 模型、Redis 缓存与限流封装、Qdrant 检索适配层。
- 生成前端对话页、结果表格、ECharts 图表推荐组件。
- 生成数据模拟脚本与评测脚本骨架。
- 生成后均经人工评审：补充异常处理、修正命名、收敛日志与错误码。

### 2.3 重构
- 将“理解问题 → 检索 → 生成 → 校验 → 执行 → 组织结果”从单个长函数拆分为可测试的独立步骤。
- 抽取统一的大模型适配层，屏蔽不同 API 差异。
- 重构以既有测试通过为前置条件，重构后回归全部用例。

### 2.4 排错
- SQL 执行报错时，码道协助分析 sqlglot 解析异常与方言差异。
- 排查缓存键冲突：定位到相对时间问题未纳入规范化 SQL，改为结合数据版本生成键。
- 排查向量检索召回不稳定：调整集合权重与实体值匹配优先级。
- 每个案例保留“现象 → 分析 → 修复 → 验证”的完整记录。

### 2.5 提示词工程
- 与码道共同迭代 NL2SQL 提示词：表摘要常驻、字段细节按检索注入、强制输出可解析格式。
- 设计拒答与澄清策略的提示词约束，人工校验后接入。

### 2.6 测试与评测
- 生成 30~50 题评测集的题型分布草案（单表、多表、口径、追问、拒答）。
- 编写安全测试样例：多语句、写操作、危险函数、系统库访问。
- 将评测接入脚本，每次修改提示词或检索策略后重新评测并记录变化。

## 3. 收益与边界

| 维度 | 结论 |
| --- | --- |
| 提效 | 待填（按实际记录：主要模块的初稿生成时间对比） |
| 质量 | 单元测试与评测集覆盖关键路径；安全规则 100% 拦截需人工复核 |
| 风险控制 | 生成的 SQL 与安全规则不直接上线，必须人工评审 + 测试验证 |

**边界说明**：码道生成的代码与建议存在错误（见 `codearts_proof/04_debug` 中未采纳案例），因此所有涉及数据库权限、敏感字段与提示注入防护的实现均由人工逐行复核。AI 负责初稿与查错，人负责判断与验收。

## 4. 结论

码道在项目中承担了“方案讨论者 + 代码初稿作者 + 查错助手”的角色，使开发精力集中在业务语义层设计、安全设计与评测体系上。项目最终质量由测试与评测数据证明，而非由 AI 生成比例证明。
