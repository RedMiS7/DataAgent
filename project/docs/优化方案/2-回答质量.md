## 2.2 结构化意图、程序检查、反问

**流程**
1. 意图识别取代现在的路由调用：一次调用输出 JSON，同时包含 `route` 和意图。用户手动选了模式时，也调用这一步。
2. 程序检查意图。
3. 不通过时返回 `clarify` 状态，带反问。
4. 通过后，把意图交给查数 Agent，2.3 按它检查 SQL。
5. 回答里展示"我理解为：……"。

**意图的字段**

| 字段 | 必填 | 内容 | 程序怎么检查 |
| --- | --- | --- | --- |
| `route` | 是 | query / analysis / direct | 取值合法 |
| `metrics` | 是（direct 除外） | 从语义层里选的指标名；语义层没有时，写出自定义的算法说明 | 指标存在；匹配到多个候选算歧义 |
| `time_range` | 否 | 用户说的时间原话 | 程序的时间解析能解析出来，结果和意图一致。缺失时按最近 30 天，回答里写明"未指定时间，按最近 30 天统计" |
| `comparison` | 分析、对比类必填 | 对比期 | 能解析 |
| `dimensions` | 否 | 分组的维度 | 字段存在 |
| `filters` | 否 | 筛选的字段和取值 | 字段存在；取值在实体值索引里能找到 |
| `result_shape` | 是 | 单值 / 前 N 名（N、方向）/ 分组 / 趋势（粒度）/ 明细 / 两期对比 / 比率 | 取值合法；前 N 名要有 N |
| `missing` | 否 | 模型认为缺少的信息 | 非空就反问 |

**反问规则**
1. 以下情况返回 `clarify`，带一句反问和 2～4 个可选项：
   - 必填项缺失；
   - 指标匹配到多个候选；
   - 筛选值找不到；
   - `missing` 非空。
2. 用户回答后，和上一轮的意图合并，再检查一次。
3. 同一个问题最多反问 2 轮。之后仍然缺的项按默认值处理，回答里写明假设。
4. 追问省略了内容时（"那上个月呢"），沿用上一轮的意图，不反问。

**涉及文件**
- `backend/app/agent/router.py`：改为意图识别
- `backend/app/agent/pipeline.py`
- 回答结构：增加 `clarify` 状态、反问内容、意图
- 前端：反问卡片（可选项按钮）、"我理解为"的展示
- 评测：期望意图和"是否应该反问"（计划 1 的 1.4）

**测试**
- 每个字段的检查各有通过和不通过的用例。
- 缺指标、多个候选指标、筛选值不存在时反问；没说时间时不反问，并写明按最近 30 天。
- 反问两轮后不再反问。
- 追问沿用上一轮的意图。
- JSON 解析失败时，重试一次；还不行就按查询模式处理，并记录日志。

## 2.3 SQL 和意图的一致性检查

**改法**

在 `run_sql` 执行 SQL 之前，用 `sqlglot` 解析 SQL，和意图逐项对照：

| 检查 | 不通过的例子 |
| --- | --- |
| 时间条件和意图的时间范围一致（由现有的 `time_range_warning` 扩展） | 问"上个月"，SQL 写成本月 |
| 用到了指标定义要求的表 | 退货率没有用到退款表 |
| 分组字段包含意图里的维度 | 问"各渠道"，没有按渠道分组 |
| 结果形式一致 | 问比率但没有比值列；问"哪个"却返回多行；问前 N 名但没有排序 |
| 筛选条件都在 WHERE 里 | 问"河南省"，没有筛选省份 |
| 一对多关联后直接计数 | 订单关联订单明细后用 `COUNT(*)` 数订单（关联关系从语义层的关联说明和表的主键读取） |

不通过时，把原因作为 `run_sql` 的返回信息交给模型，让它修正后重试，处理方式和 SQL 安全校验拦截时一样。

**涉及文件**
- `backend/app/agent/tools.py`
- 新增 SQL 和意图对照的模块

**测试**
- 每项检查各有正例和反例，确认不会误报。
- 把评测里的 i02（没算比率）、f05（返回 10 行）作为回归用例。

## 2.4 结论带依据

**结论格式**（JSON）

```json
{
  "judgement": "一句判断",
  "points": [
    {
      "claim": "说法",
      "evidence": [{"query": 1, "rows": [0, 1], "columns": ["期间", "退货率"]}]
    }
  ],
  "advice": "可以执行的建议"
}
```

**依据的要求**（写进提示词）
- 分析题至少要有三类依据：
  - 前提：两期的总体数字；
  - 主要来源：贡献最大的几项（计划 3 的 3.1 拆解工具算出的结果；3.1 完成之前由模型自己写 SQL 计算）；
  - 对照：其他维度变化不大，或者变化分散在多项里（适用时）。
- "没有单一主因"要用贡献分布作为依据。
- 查询题：一句话结论 + 1 条依据。

**程序处理**
1. 解析 JSON。引用的查询、行、列不存在时，带上错误原因让模型重写一次。
2. 还不行，就展示模型原文和所有查询的表。
3. 页面上每条要点旁边显示依据的小表格，可以展开看 SQL。
4. `[查询n]` 引用由依据自动生成。

**涉及文件**
- `backend/app/agent/planner.py`：汇总提示词和解析
- `backend/app/agent/pipeline.py`：查询模式的结论格式和解析
- 回答结构：增加 `points`、`evidence`
- 前端：`AnswerCard`

**测试**
- 正常 JSON、引用越界、JSON 格式错误三种情况的处理。
- 依据表格展示的数据和查询结果一致。

## 2.5 查询结果的合理性检查

**改法**
- 以下情况作为 `run_sql` 的返回信息提示模型检查：
  - 比率超出 0～100%；
  - 件数、金额为负；
  - 意图要求有数据但结果为空。
- 分组结果：和同一指标不分组的总数对照，不一致时提示。

**涉及文件**
- `backend/app/agent/tools.py`

**测试**
- 每种情况各有正例和反例。
