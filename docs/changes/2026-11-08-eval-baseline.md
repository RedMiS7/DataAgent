# 评测补充指标和用例，跑出优化前的基线

日期：2026-11-08

## 做了什么

这是[问答流程优化方案](../问题记录/问答流程优化方案.md)的第 0 步：只改评测，不改问答流程本身。

评测代码：

- `eval/runner.py`
  - 新增 `ToolProbe`：评测时包住 `run_sql` 和 `describe_table` 调用的函数（`validate_and_limit`、`execute_sql`、`describe_tables`），记录每道题提交了几条 SQL、失败几条、其中几次是字段不存在（校验器报"字段不存在"或 MySQL 报 `Unknown column`）、查了几次字段。问答流程本身不受影响。
  - 新增宽松比对 `compare_rows_loose`：允许多出的列和任意列顺序，每一行期望值都要在实际结果的某一行里找到。用例写 `"match": "loose"` 时用它判定是否通过；其他用例仍按原来的严格比对判定，同时记录宽松比对的结果。
  - 新增 `failure_hint`：给失败的题自动标注现象（列数不同、行数不同、日期不同、用的表不同、数值不同、没有结果、字段不存在后未恢复、没有参考答案等），作为人工标注原因的起点。
  - 新增 `report_metrics`：结果文件的 `summary.metrics` 里汇总 SQL 无报错的题占比、SQL 条数和失败条数、字段不存在次数、`describe_table` 次数、平均模型调用次数和 token、宽松比对通过数、失败现象分布。
  - 用例支持两种新的历史写法：`turns`（先真实地问一遍前面的问题，按前端 `buildHistory` 的规则组成历史）和 `history_messages`（直接写出前端发送的历史）。
  - 新增 `direct` 类用例的判定：状态为 `text` 且没有 SQL 才算通过。
- `eval/run_eval.py`：打印上面的指标，失败题后面附上失败现象。

评测用例：

- `eval/questions.json` 新增 8 题。
  - `multiturn` 5 题（t01 到 t05）：追问换维度、换分组、加指标；上一轮失败、只剩用户问题时再问；真实历史下的"那上上个月呢"。
  - `direct` 3 题（d01 到 d03）：解释口径、问能力范围、改写上一轮的结论。用自动模式跑，和前端默认一致。
- `eval/routing_cases.json` 新增 7 题：6 题期望 `direct`，1 题"GMV如果算上运费，上个月是多少？"期望 `query`，防止以后把需要查数的问题判成直接回答。

测试：

- 新增 `backend/tests/test_eval_runner.py`，13 个测试，覆盖宽松比对、调用记录、失败现象、指标汇总、多轮历史、直接回答判定和新用例格式。

结果文件：

- `eval/results/baseline-2026-11-08.json`：这次的基线。`latest.json` 没有覆盖。

## 为什么做

后面几步要改历史、路由、失败处理和字段上下文，需要一个基线来判断改动有没有效果。原来的评测只看最终结果对不对，看不到字段报错、重试和查字段的次数，也没有覆盖"追问要依赖上一轮的查法""不需要查数的问题"这两类问题。

### 失败题的原因（人工标注）

逐题看了 SQL 和参考答案：

| 题 | 现象 | 原因 | 归类 |
| --- | --- | --- | --- |
| m03、m04、m07、i03、f03 | 列数不同 | 结果正确，只是多带了一列（如 ROI 旁边带上 GMV 和花费），宽松比对都通过 | 评分口径 |
| m05、i05 | 数值不同 | 结果正确，参考答案四舍五入到 1 位小数（201.8），模型没有四舍五入（201.84），差值超过 0.02 的容差 | 评分口径 |
| f05 | 行数不同 | 问"哪个商品卖的最差"，模型返回了 5 行，结论说对了第一名 | 评分口径（模型也可以更贴合问题） |
| i02 | 列数不同 | 问退货率，模型只查了退款金额和 GMV，没有算出比率，结论只是罗列两个数 | 口径错 |
| t01 | 日期不同 | "按渠道拆一下"没有被识别成追问，时间没有继承"上个月"，查成了最近 30 天 | 时间错 |
| t04 | 行数不同 | 上一轮失败，历史里只剩用户问题、没有回答；模型去回答了上一轮"各省份退款金额"，没有回答"订单数" | 历史结构（方案第 2 步要修的问题） |
| d01、d02 | 状态为 error | 模型没有调用 `run_sql`，被记为失败："模型没有调用 run_sql 工具" | 不查数就报错（方案第 3 步） |
| d03 | 没有直接回答 | "把这个结论写成一段话"又去查了一遍，而且时间没有继承，查成了最近 30 天的 GMV，给出的数字是错的 | 不查数的问题 + 时间错 |
| n02、n06、n15 | 数字未核对 | 分析结论里有数字没能在查询结果中核对上 | 其他（沿用原有的判定，这次没有逐个分析） |
| a01 到 a04 | 没有参考答案 | 归因题没有 `expected_sql`，在问答评测里按行数比对一定失败；归因评测另外判定，4/4 通过 | 评分问题 |

### 从基线看出的结论

- **字段不存在已经很少**：136 条 SQL 只有 2 次，而且都恢复了。代价是 38 次 `describe_table`，平均每题 0.6 次额外的工具调用。方案第 5、6 步的主要收益应该是减少这些查字段的调用和 token，而不只是减少报错。
- **真正的错误集中在时间、历史结构和不查数的问题**：t01、d03 是追问没有继承时间；t04 是方案第 2 步要修的问题；d01 到 d03 是方案第 3 步要修的问题。基线都复现出来了，后面可以直接对比。
- **新发现的问题**："按渠道拆一下""把这个结论写成一段话"这类追问不会被 `FOLLOWUP_PATTERN` 识别，时间不会继承。方案里还没有这一条，需要决定放进哪一步。
- **约 8 题的失败是评分口径造成的**（多出的列、四舍五入、返回行数），实际答案是对的。严格比对的准确率偏低，看效果时建议同时看宽松比对。是否修改评分规则需要另外决定，这次没有改，保持和以前的结果可比。
