## 1.2 评测账号

**改法**
1. 新增数据库账号，配置项为 `MYSQL_EVAL_USER`、`MYSQL_EVAL_PASSWORD`，账号名默认 `dataagent_eval`。密码只写在 `.env` 里，`.env.example` 只写变量名。
2. 权限：
   - 各数据集的视图库只读（`safe`、`dabench`，以及以后导入的数据集）；
   - 应用库（`dataagent`、`dataagent_dabench`）只读；
   - 评测表（1.3 的 `eval_runs`、`eval_case_results`）可以写；
   - 不授权原始库（`shop`、`dabench_raw`），不能建表、删表、改表结构。
3. 授权方式：
   - 新增命令 `python -m app.semantic.cli grant_eval_user`，可以重复运行，给已有的库补齐权限；
   - `import_dataset` 导入新数据集时，同时给评测账号授权视图库。
4. 连接：
   - `config.py` 增加评测账号的配置；
   - 增加 `eval_business_url(db)` 和 `eval_app_url()` 两个连接地址；
   - 写法参照 `docs/changes/2026-11-09-app-db-account.md` 里服务账号 `dataagent_app` 的做法。
5. 评测里的分工：

   | 做什么 | 用哪个账号 | 约束 |
   | --- | --- | --- |
   | 被测的问答 | `shop_ro`，保持不变 | Agent 的安全策略 |
   | 参考 SQL、`facts` 检查点 | 评测账号 | 只允许 SELECT，有执行超时；不套用 Agent 的 `sql_policy`，不限 500 行 |
   | 读取问答记录 | 评测账号 | — |
   | 写入评测记录 | 评测账号 | — |

6. 以后要加"检查回答有没有泄露隐藏字段"的安全题时，只给评测账号授权那几个隐藏列，按列授权。

## 1.3 评测打包进应用并入库

**改法**
1. 评测代码进入后端：
   - `eval/runner.py`、`eval/retrieval_eval.py` 挪到 `backend/app/evaluation/`；
   - 评测题按数据集清单打进镜像（计划 3 的 3.5）；
   - 运行命令：`docker compose exec app python -m app.evaluation run --mode all`，直接用实例里保存的 key 和配置；
   - `eval/run_eval.py` 保留，作为本机运行的入口，调用同一套代码。
2. 新增两张表（应用库）：
   - `eval_runs`：
     - `id`、`dataset`、`mode`、`categories`、`repeat`、`concurrency`
     - `status`：`running`、`done`、`failed`、`cancelled`
     - 进度：`done` / `total`
     - `started_at`、`finished_at`
     - 运行信息：模型、`schema_mode`、git 提交号、是否开缓存
     - `summary`（各组分数，JSON）、`error`
   - `eval_case_results`：
     - `run_id`、`case_id`、`attempt`、`dataset`、`kind`、`category`
     - `passed`、`scored`、`detail`、`failure_hint`
     - `sql`、`summary`、`summary_source`、`warnings`
     - `log_id`（关联 `query_logs`）
     - token 和耗时
3. 运行时：
   - 每题跑完立刻入库，同时导出 JSON 文件，格式和现在兼容；
   - 评测产生的问答记录标为 `source=eval`；
   - 同一个实例同一时间只允许一个评测，有 `running` 记录时拒绝，并提示它的编号；
   - 启动时把遗留的 `running` 记录标为 `failed`；
   - `--resume <run_id>`：跳过已入库的题，从断点继续。
4. 查看命令：
   - `python -m app.evaluation list`：评测列表和各组分数；
   - `python -m app.evaluation show <run_id>`：分组分数、不计分的题，以及失败题的 SQL、结论和失败原因；
   - `python -m app.evaluation compare <a> <b>`：新通过、新失败的题和波动范围。
5. 更新 `CLAUDE.md` 里的评测命令。

- `data/initdb/02_app_schema.sql`

## 1.4 判分修正

**改法**

| 项 | 改法 |
| --- | --- |
| 数值比较 | 实际值先按参考值的小数位四舍五入，再比较 |
| 多出列 | 宽松比对作为主分数：参考 SQL 的每一列都要能在答案里找到。严格比对作为参考指标保留 |
| 没有判分依据的题 | 既没有 `expected_sql`、也没有 `facts` 的题，标为"没有判分依据"，照常运行和记录，但不计分，单独列出 |
| 分析题的"数字未核对" | 删除这个判分条件（配合计划 2 的 2.1） |
| 意图和反问 | 题目可以写期望的意图和"是否应该反问"，按字段统计意图准确率、漏问率、多问率（配合计划 2 的 2.2） |
| `facts` 检查点 | 题目可以写 `facts`：参考 SQL，加上结论里必须提到的内容。每个数据集的检查点写在它自己的评测集里 |

改动前后各跑一次，改动文档里同时写出新旧两种算法的分数。

**涉及文件**

**测试**

## 1.5 多次运行和并发运行

**改法**
- `run --repeat N`：每组写出平均值、最低、最高，以及每道题 N 次全部通过的比例（pass^N）。
- `run --concurrency N`：默认 4，用线程池执行。多轮题整道作为一个任务。
- `compare <a> <b>`：见 1.3。

**测试**
- 用假的问答流程：`--repeat 3` 的统计结果正确。
- 并发运行时，多轮题的轮次顺序不乱。

## 1.6 后端指标（判断要不要接入 Redis、Kafka）

**改法**
1. `call_traces` 增加以下几类调用的记录，每条带耗时、是否成功、错误类型：
   - 回答前的语义检索；
   - `search_semantic` 工具内部的 embedding 和重排；
   - SQL 执行。
2. 错误类型分为：超时、429、5xx、其他。
3. `query_executions`（1.1）增加 `sql_hash`；embedding 和重排的调用记录也带上输入内容的哈希。
4. 评测结果里按组输出以下指标：

| 指标 | 怎么算 | 对应 Redis、Kafka 能解决的问题 |
| --- | --- | --- |
| 每题耗时拆分 | 模型、SQL、embedding、重排、其他各占多少 | 哪一段值得缓存 |
| 重复请求比例 | 同一次评测内，相同 `sql_hash`、相同 embedding 输入、相同重排输入出现的次数 | SQL、embedding、重排缓存的命中上限 |
| 429 和超时次数 | 按服务分别统计，并发 1 和并发 4 各跑一次 | 是否需要全局的模型并发令牌桶 |
| 降级次数 | 重排、embedding 降级的次数（计划 4 的 4.1） | 是否需要熔断 |
| 长耗时问题 | 超过 60 秒的题数，分析模式的最长耗时 | 是否需要把长任务改成异步 |
| 写日志耗时 | `_finalize` 里写 `query_logs`、`call_traces` 的耗时 | 是否需要把日志移出请求路径 |

5. `python -m app.evaluation show <run_id>` 输出上表。

- `backend/app/semantic/retriever.py`、`backend/app/semantic/table_search.py`

## 1.7 离线评委模型

只在离线评测里用，不进入线上问答。

**用途**

| 用途 | 输入 | 输出（JSON） |
| --- | --- | --- |
| SQL 是否符合意图（没有参考 SQL 的题） | 问题、意图、SQL、相关的指标口径和表结构、结果前若干行 | 是否符合；不符合的地方；错误类别 |
| 失败原因归类 | 同上，再加参考答案 | 理解错 / SQL 写错 / 解读错 / 判分误判 |
| 分析结论是否合理 | 问题、每条要点和它的依据、检查点 | 每条说法能否被依据支撑；没有依据的因果判断；漏掉的主要原因 |
| 结论和依据是否一致 | 要点的说法、依据数据 | 一致 / 不一致 |

**规则**
- 有参考答案的题，用参考答案比对，不交给评委。
- 评委的理由必须引用原文。
- 先用人工标注的样本校准，一致率达到 85% 以上才计入分数。
- 评委尽量用和被测模型不同的模型。
- 结果缓存：key 包含评委模型、评委提示词版本和回答内容的哈希。

**涉及文件**
- `backend/app/evaluation/judge.py`（新）
- 评测题文件：检查点和人工标注

**测试**
- 用固定的评委回复（不调真实模型）测试解析、缓存和计分。
- 人工标注集上算出一致率。

## 完成标准

| 项 | 标准 |
| --- | --- |
| 复查 | 每道失败题都能看到结论原文和每条中间查询 |
| 后端指标 | 评测结果里能看到 1.6 的六项指标 |
| 运行 | 一条 `docker compose exec` 命令跑完评测，不用挂目录 |
| 参考答案 | 不再被 500 行上限截断 |
| 波动 | 每次评测跑 3 次，写出波动范围 |
| 耗时 | 并发 4 时，一次全量评测在 6 分钟左右（估算，以实测为准） |
| 评委 | 和人工的一致率达到 85% 以上 |
