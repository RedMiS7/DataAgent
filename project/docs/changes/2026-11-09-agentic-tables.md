# 模型按问题检索表

日期：2026-11-09

## 做了什么

这是[问答流程优化方案](../问题记录/问答流程优化方案.md)的 8.3：把 8.2 的按表检索接进问答。系统提示词里不再放全部表结构，只放一份表目录和上一轮用到的表；其他表由模型自己调用 `search_semantic` 检索。

**两种模式**（`backend/app/config.py`、`.env.example`）

- 新增 `schema_mode`：`agentic`（默认）和 `full`（第 6、7 步的做法，所有表的全部字段都放进提示词）。读不到真实字段时，两种模式都退回只放检索到的字段。

**提示词**（`backend/app/semantic/schema_context.py`、`backend/app/agent/pipeline.py`）

- `build_agentic_context`：
  - **【表目录】**：每张表一行，表名和摘要。10 张表约 300 token。超过 `schema_token_budget` 时去掉摘要，只剩表名也超过时就不放。
  - **【上一轮用到的表】**：最近 3 条回答的 SQL 用到的表，按最新的在前列出全部字段，用目录剩下的预算。追问时这些表不用再检索。
- 系统提示词的顺序：规则、数据库说明、表目录、上一轮用到的表、时间范围、检索到的口径和案例。表目录每题都一样，放在前面方便命中缓存。`agentic` 模式下不放检索到的【字段】和【表摘要】，以免和表目录重复。
- 规则 2、11 拆成常量，`agentic` 模式下用 `agentic_rules` 换成：
  - 第 2 条："表名照【表目录】和检索结果的写法写"。
  - 第 11 条："写 SQL 前，先调用 search_semantic 检索要用的表……检索结果和【上一轮用到的表】里列出的表包含全部字段……SQL 只能用检索结果、【上一轮用到的表】或 describe_table 里出现过的表；缺表时再检索一次。不需要查数时不用检索。"
- 第 5 条里的"【表结构】的字段说明"改为"表结构里的字段说明"，两种模式都适用。
- 分析模式的每一步用同一份提示词和工具，各自检索；规划员不变。

**工具**（`backend/app/agent/tools.py`、`backend/app/semantic/table_search.py`）

- `agentic` 模式下 `search_semantic` 换成按表检索：
  - 调用 8.2 的 `TableSearcher`，在线程里执行，不阻塞同时执行的分析步骤。
  - `render_search` 返回检索到的表（全部字段，表名后注明被选中的原因）和命中的指标口径、案例、实体值。
  - 总量不超过 `schema_token_budget`，超出时先去掉得分最低的选中表，补全加进来的表保留。
  - 每次检索记一条日志：耗时、检索语句、每张表和它的来源、重排没有生效的原因。
  - 检索器每题新建一次，因为重排用的 key 可能在启动后才在网页上保存。
- **表必须检索过**：
  - `AgentRunContext` 记录模型看过全部字段的表 `visible_tables`，包括放进提示词的、检索到的、用 `describe_table` 查过的。
  - `run_sql` 校验通过后，`unseen_tables` 检查 SQL 用到的表。有没看过的表就不执行，返回"SQL 用到的表还没有检索过：……先调用 search_semantic 检索这些表……"，并计入连续失败次数。
  - `full` 模式不做这项检查。
- 校验器（`backend/app/safety/validator.py`）：`SafeSQL` 新增 `tables`，即查询读的表，不含 CTE。

**子查询和 CTE 别名的提示**（`validator.py`）

字段写在子查询或 CTE 的别名上时，提示写出这个子查询有哪些列和最接近的列，例如"字段不存在：cur.gmv，子查询 cur 里没有 gmv 这一列。子查询 cur 的列：pid, refund_amt"。原来会提示"查询里没有叫 cur 的表或别名"，这句话不对。

**评测**（`eval/runner.py`、`eval/run_eval.py`）

- 每题统计 `search_semantic` 的调用次数和"用了没检索过的表"被打回的次数，打回计入 SQL 失败。
- 结果文件记下 `schema_mode`，可以用环境变量 `SCHEMA_MODE` 切换模式对比。

**测试**

- 新增 `backend/tests/test_agentic.py`，19 个测试：
  - 表目录、上一轮用到的表、预算；规则替换；`agentic` 提示词的内容和顺序；按配置选模式；
  - 检索结果的写法、超出预算时保留补全的表、什么都没找到；校验器给出的表；
  - 只放行看过的表、打回计入失败上限、`describe_table` 让表变为可见；`agentic` 模式用新的检索工具；
  - 3 个端到端用例（脚本模型，走真实的 Agent 循环）：没检索就写 SQL 被打回、检索后执行成功；上一轮的表不用检索；`full` 模式不检查。
- `test_column_check.py`：子查询和 CTE 的提示，2 个测试。
- `test_schema_context.py`：适配第 5 条规则的新写法和两种模式。

## 为什么做

第 6 步把全部表放进提示词，在 10 张表的库上效果好，但库变大就放不下，而且每道题都带着用不到的表。按方案，改由模型决定要不要检索、检索什么，程序负责把表找全（8.2）、并保证 SQL 只用看过全部字段的表。

## 有什么用

- 提示词里只有表目录和上一轮的表，库变大后不会把提示词撑满。
- 模型写 SQL 前一定看过要用的表的全部字段。没看过就写，程序会打回，不靠提示词约束。
- 追问直接带上上一轮的表，不用再检索一次。
- `full` 模式保留，可以随时切回去对比。

## 如何验证

运行过的命令和结果：

- `cd project/backend && PYTHONPATH=. ../../.venv/bin/python -m pytest -q`：392 passed，1 skipped（集成测试）。
- `cd project && ../.venv/bin/ruff check backend eval data`：All checks passed。
- 重建容器后，在容器里用真实模型（`agentic` 模式）问了两道题：
  - "最近30天各渠道的订单数是多少？"：模型先检索"最近30天各渠道的订单数"，再写出关联 `channels` 的 SQL，状态 ok，模型调用 3 次，10.5 秒。
  - "上个月各承运商的平均签收时长是多少小时？"：先检索一次，SQL 关联 `orders` 和 `shipments`，状态 ok，模型调用 3 次，16.4 秒。

**没有验证的内容**：

- **`agentic` 和 `full` 的完整对比评测没有跑完**。原计划各跑两次 `--mode all`，第一轮开始 3 分钟后按用户要求停止，没有产生结果。所以不知道 `agentic` 在准确率、模型调用次数、token 和耗时上和 `full` 比怎么样。
- 默认模式已经是 `agentic`，**线上现在用的就是还没做完整评测的新链路**。需要时可以设置 `SCHEMA_MODE=full` 切回。
- 前端没有专门显示"检索表"这一步，它和其他状态一样显示文字。
- 分析模式下，几个步骤共用一份"看过的表"：一个步骤检索过的表，另一个步骤直接用也不会被打回，哪怕那个步骤的 Agent 没看过这张表的字段。字段写错仍然会被字段校验拦下。
