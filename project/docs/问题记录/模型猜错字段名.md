# 模型猜错字段名

日期：2026-11-06

状态：查询和分析模式都已接入 `describe_table`，字段报错减少，但没有完全消失

## 现象

分析模式下，思考过程偶尔出现 SQL 执行失败，MySQL 报 1054（字段不存在）。模型收到报错后会重写 SQL，所以最后回答正常，但耗时和查询次数都会增加。

已确认的错误：

| 模型写的字段 | 真实字段 | 所在表 |
| --- | --- | --- |
| `cost` | `spend` | `ad_daily_stats` |
| `revenue` | `attributed_gmv` | `ad_daily_stats` |
| `amount` | `refund_amount` | `refunds` |

## 原因

模型没见过这个数据库，只能根据提示词里的字段写 SQL。

- `retrieval_top_k=6`：检索只给最相关的 6 个字段。这个值是项目首次提交时的默认值，没有实测依据。
- 检索只看用户这句话。“有什么建议？”几乎没有关键词，检索结果里没有 `spend`。
- 分析模式要跨多张表查询，比查询模式更容易缺字段。
- 模型能看到表简介，但看不到列名，就按常见叫法猜。

这不是上下文窗口不够。这次问答开始时，提示词和历史约 3700 字，模型上限是 65536 tokens。

## 排查方法

当时 Docker 和 `query_logs` 里都没有这次失败，失败的 SQL 是从 MySQL 统计里找到的：

```sql
SELECT LAST_SEEN, QUERY_SAMPLE_TEXT
FROM performance_schema.events_statements_summary_by_digest
WHERE SUM_ERRORS > 0
ORDER BY LAST_SEEN DESC;
```

现在可以直接看后端日志：

```bash
cd project && docker compose logs -f app
```

## 方案选择

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 调大 `retrieval_top_k` | 不用 | 指标和案例也会变多，开放问题仍可能漏字段 |
| 把全部字段放进提示词 | 不用 | 字段变多后不好扩展，每轮都带着用不到的内容 |
| AgentScope Skill | 不用 | 一次只能看一个 Skill，还要把字段转成 Skill 内容 |
| 文件路径 + 读文件工具 | 不用 | 字段说明要再存一份，模型还要有读文件权限 |
| `describe_table` 工具 | 采用 | 按需查看，一次可查多张表，直接读现有数据 |

## 修复

两种模式都接入了 `describe_table`。它以 `safe` 库的真实字段为准，再合并 `semantic_schema_items` 里的说明。这样即使以后新增字段还没写说明，模型也能看到字段名。

原来说明表只收录了 69 个字段中的 47 个，缺少 `campaign_id` 这样的关联字段，现在已全部补齐。

字段不存在时，`run_sql` 的报错还会提示模型先查字段。

## 验证结果

用真实模型跑同样 9 个分析问题，问题各跑一次，其中“有什么建议？”跑三次：

| 提示词 | 字段报错 | 模型提前查字段 |
| --- | --- | --- |
| 字段不在列表里时先查 | 3 次 | 1 次 |
| SQL 用的每个字段都必须见过，否则先查 | 0 次 | 4 次 |

第一版工具已接入，但模型常常先猜；3 次报错后都改用 `describe_table` 恢复了。第二版改了规则后没有再报错。

后来把规则移到两种模式共用，并补全字段说明，再跑一次同样的 9 个问题：1 次字段报错（`r.created_at`），3 次查字段，全部成功。所以规则能减少猜错，但不能完全避免。

## 补字段说明时的副作用

22 个字段全部参与检索后，44 个问题里有 39 个的检索字段变了。`ad_daily_stats.id`、`customers.name` 这类字段挤掉了 `channels.name` 这样有用的字段。

处理方式是把 18 个低价值字段设成 `enabled=0`：不参与检索，但 `describe_table` 仍能看到说明。之后只有 5 个问题的检索字段有变化。

## 还没做

- 模型仍可能先猜再查，比如把 `paid_at` 写成 `created_at`。报错后能恢复，但会多一轮。
- 完整评测还没跑，接入查询模式的效果只有 17 个问题的抽样。
