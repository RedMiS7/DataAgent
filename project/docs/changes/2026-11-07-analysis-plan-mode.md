# 分析模式改为先规划再执行

日期：2026-11-07

## 做了什么

分析模式不再由一个 Agent 自己决定查什么，改为：规划 → 各步骤同时执行 → 补查一次 → 汇总。路由不变，仍然只在查询和分析之间二选一；手动选“分析”时也走这套流程。

### 流程

整个分析放在同一个 `asyncio.run` 里，规划、各步骤、补查、汇总共用一个模型实例。

1. **规划**：调用 1 次模型，不带工具，超时 20 秒。输入是对话记录、最后一个问题、本期和对比期、知识库检索到的字段和口径。输出 `{"steps": [{"goal": "..."}]}`，最多取 4 步，每步只写要看什么，不写 SQL。提示词写明所有步骤会同时执行、互相看不到结果，需要根据结果往下钻的查询留给补查。
2. **同时执行各步骤**：每一步启动一个小 Agent，工具和查询模式相同（`run_sql`、`describe_table` 等），轮数上限也和查询模式相同。各步骤用 `asyncio.gather` 同时执行，输入是用户问题和本步任务。没有执行成功任何查询的步骤标记为失败，不影响其他步骤。
3. **补查**：第一轮全部完成后，把计划和结果交回规划器，最多再加 1 步，也可以不加，超时 20 秒。补查的步骤能看到第一轮的结果摘要（每条查询列出前 5 行和本步小结）。
4. **汇总**：调用 1 次模型，不带工具，超时 60 秒。根据计划和每步结果（每条查询最多 20 行）写结论，格式和原来一样：一句判断、2 到 4 条带 `[查询N]` 的要点、一条建议。写完后照常做引用整理和数字核对。

### 查询次数

- 每一步最多 2 条查询，超出时 `run_sql` 返回“这一步的查询次数已用完”。
- 计划 4 步、补查 1 步，每步 2 条，合计不超过原来的 10 条上限，各步骤不会互相抢额度。
- 总上限按“已成功加执行中”的查询计数（`AgentRunContext.reserved`），多个步骤同时执行时也不会超过。查询次数用完后不再补查。

### 为同时执行做的调整

- `run_sql` 和 `describe_table` 改为 async，数据库操作用 `asyncio.to_thread` 放到线程里执行。AgentScope 直接在事件循环里调用同步工具，一个步骤跑 SQL 时会卡住其他步骤。
- 查询编号在查询成功时才确定，各步骤完成的先后不固定，所以编号顺序每次可能不同。
- `build_toolkit(context, step_id, step_limit)`：每一步有自己的工具集，查询所属步骤和本步查询次数都在建工具时确定。
- 分析模式的查询状态只在查询完成后推送一行，带上步骤号，例如“第2步 · 查询 3：……，返回 12 行”。

### 超时

- 规划、补查、汇总和路由这四个不带工具的 Agent 设置了 `ReActConfig(interruption_raise_cancelled_error=True)`。AgentScope 默认会吞掉任务取消，返回固定回复“I notice the interruption. How can I help you?”，`asyncio.wait_for` 超时时就不会抛出 `TimeoutError`。
- 时限放宽：规划和补查 20 秒，汇总 60 秒，路由由 8 秒改为 15 秒（`router.py` 的 `ROUTER_TIMEOUT_SECONDS`）。评测中规划有 2 题超过了原来的 10 秒。

### 数字核对

- 数字核对改为对照本次回答的全部查询，不再只看结论引用到的查询。结论常有引用编号写错、建议行不写引用的情况，原来会把这些数字误报为未核对。
- 结论用到了未引用查询里的数字时，那条查询也会显示在答案中。
- 排查过程见 `docs/问题记录/结论数字被误报为未核对.md`。

### 出错时的处理

| 情况 | 处理 |
|---|---|
| 规划超时、出错、JSON 解析不出来或没有步骤 | 改用原来的单 Agent 分析流程，推送 `plan_fallback` 状态，写 warning 日志（含模型原始回复或异常堆栈） |
| 补查超时、出错或解析不出来 | 跳过补查，写 warning 日志 |
| 某一步抛异常 | 记录异常堆栈，标记为失败，其他步骤照常完成 |
| 所有步骤都没有查到数据 | 返回 error，不调用补查和汇总 |
| 某一步调用了 `decline_request` | 返回 refused，不调用补查和汇总；同一轮的其他步骤已经开始，会执行完 |
| 汇总超时或出错 | 使用模板结论 |

### 接口

- SSE 新增两种事件：`plan`（整份计划，生成和补查后各推送一次）和 `step`（某一步的状态变为 running、done 或 failed）。
- `AnswerPayload` 新增 `plan`：每一步的 `id`、`goal`、`origin`（plan 或 supplement）、`status`。没有计划时为空列表。
- `QueryResult` 新增 `step_id`：这条查询属于第几步；单 Agent 流程中为 `null`。

### 前端

- 思考面板顶部显示计划清单，实时显示每一步的状态和耗时，补查的步骤带“补查”标签。回答结束后仍未完成的步骤显示为“未执行”。
- 有计划时，下方状态行不再显示耗时。各步骤同时执行，两行之间的间隔不是任何一步的耗时。
- 答案卡片里的查询按步骤分组，每组上方显示“第 N 步：要看什么”。没有计划时显示方式不变。

### 评测

- `eval/questions.json` 的分析题从 5 道补到 15 道，每题新增 `expected_dimensions`，标注应该覆盖的维度。
- `eval/runner.py` 新增 `score_analysis`：状态为 ok、结论由模型生成、计划和查询覆盖了全部应覆盖的维度、没有未核对的数字，才算通过。问答评测中的分析题也改用这个标准。
- 新增 `--mode analysis`，只跑分析题并统计耗时；加 `--no-plan` 时跳过规划，用原来的单 Agent 流程，用于对比。

## 为什么做

原来的分析模式是一个 ReAct Agent，提示词里写了“先查整体，再按维度拆”，查什么、查几步、什么时候停都由模型临场决定。这样容易漏掉维度，或者在一个维度上反复试；用户只能看到一条条 SQL，不知道整体打算；中间一步出错会影响整轮。

先列计划再执行，查询的范围在开始时就定下来，每一步单独执行、单独失败；补查一次用来处理“先找到下滑最多的类目，再看这个类目里的商品”这类需要往下钻的问题。原来的单 Agent 流程保留，规划失败时兜底。

各步骤同时执行，是因为逐步执行太慢。逐步执行时，同一个问题要调用模型 15 次且一次接一次，耗时 32.7 秒；原流程一次回复可以发出多条查询，只调用 3 次，耗时 11.1 秒。计划常常排满 6 步再补查 2 步，还会把 10 条查询用完、漏掉重要维度，所以同时把计划缩到 4 步、补查缩到 1 步，并给每一步固定 2 条查询的额度。

## 有什么用

- 用户在思考面板里能看到分析计划、每一步的进度和耗时，答案里的数据按步骤分组，知道每组数据是为了回答什么。
- 一步失败不会拖垮整个分析，结论会说明缺了哪部分数据。
- 结论里的数字大多直接来自 SQL 结果，可以追溯。
- 评测可以统计维度覆盖、数字核对和耗时，并能和原来的流程直接对比。
