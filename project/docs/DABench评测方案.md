# DABench 评测方案

日期：2026-11-09
状态：方案，待确认（尚未改代码、评测集和提示词）

参考：

- [AI 评测分层方案](AI评测分层方案.md)：L0～L6 分层、计分规则、L5 归因判分、LLM 评委、异动注入。本文是它在 DABench 上的具体做法，原则不再重复。
- `DB/DABench.csv`：10 道题；`DB/description.md`：火山引擎的评测维度和分级。
- `data/dabench/manifest.json`、`data/seed_dabench/`：导入清单和语义层。
- `eval/dabench_reviews.json`：逐题核对记录。

## 结论

1. **DABench 现在没有任何评测数据**。DABench 实例的 `dataagent_dabench.query_logs` 是 0 条，评测脚本也没有 DABench 入口。第一件事是做出一个能跑、能重复的基线。
2. **10 道题里只有 7 道能按根因计分**：
   - 第 101 题的前提和数据不符，不计分；
   - 第 74、66 题是自由提问，没有结论答案，单独评；
   - 这次复核又发现，第 107 题严格答案里的"C 级客户减少"在数据里不成立，这一条因素不计分（见第二节）。
   - 7 道题里错 1 道就差 14 个百分点，所以报告**报题数，不报百分比**，并且每个配置跑 3 遍。
3. **不只比 SQL，分五项评**：
   - 前提判断；
   - 关键数字（`facts`）；
   - 分析思路照着做了几步；
   - 题目给的定义用对没有；
   - 根因命中。

   前四项由程序判，只有根因命中交给 LLM 评委，评委要用人工标注校准。
4. **每道题跑两种问法**：带"分析思路"的原题，和去掉分析思路、只留问题的版本。两者的差距就是"框架遵从"和"自主归因"能力的差距，正好对应 `description.md` 里的两个维度。
5. **要防过拟合**：`seed_dabench/metrics.json` 里的高利贷、闪电单、客户评级、线索 ROI、成单数都是看着这几道题写的。这些定义题目本来就会给出，影响不大，但仍要加一组"去掉题目专属口径"的对照；再用异动注入题做留出集，留出集里的题不能用来调提示词。
6. **分四层**：
   - L3 原子查数题：把每道题拆成一问一答的小题，有参考 SQL，程序判分；
   - L4 下钻多轮：按分析思路一轮一轮追问；
   - L5 完整归因；
   - 异动注入题。

   失败时能看出是查数不对、下钻断了，还是归纳错了。

## 三、题目文件

新建 `eval/dabench_cases.json`。题目原文仍然只放在 `DB/DABench.csv`，这里只放判分要用的标注。下面以第 107 题为例：

```json
{
  "query_num": "107",
  "track": "attribution_framework",
  "period": {"current": ["2024-11-01", "2024-12-01"], "base": ["2024-10-01", "2024-11-01"]},
  "premise": {"metric": "闪电单数", "direction": "down",
              "sql": "SELECT SUM(created_date < '2024-11-01'), SUM(created_date >= '2024-11-01') FROM dabench.car_leads WHERE is_ordered = 1 AND DATEDIFF(order_date, created_date) <= 7 AND created_date >= '2024-10-01' AND created_date < '2024-12-01'",
              "expected": [364, 224]},
  "factors": [
    {"id": "f1", "text": "Online_AD 渠道的线索量（闪电单）减少", "strict": true, "scored": true,
     "keywords": ["Online_AD"]},
    {"id": "f2", "text": "C 级客户减少", "strict": true, "scored": false,
     "note": "数据不支持：Online_AD 的闪电单全部来自 A 级，C 级线索 27 → 22"},
    {"id": "x1", "text": "A 级客户线索减少", "strict": false, "scored": false, "bonus": true}
  ],
  "facts": [
    {"name": "Online_AD 闪电单 10 月", "value": 283, "tolerance": 0},
    {"name": "Online_AD 闪电单 11 月", "value": 78, "tolerance": 0},
    {"name": "Online_AD A 级线索 10 月", "value": 370, "tolerance": 0}
  ],
  "framework": [
    {"id": "s1", "text": "对比 10 月和 11 月闪电单数量", "check": {"dimension": null}},
    {"id": "s2", "text": "按二级渠道分组找变化最大的渠道", "check": {"dimension": "sub_channel"}},
    {"id": "s3", "text": "在该渠道内按客户评级分组", "check": {"dimension": "客户评级", "filter": "Online_AD"}}
  ],
  "knowledge": [
    {"name": "闪电单 ≤ 7 天", "sql_pattern": "DATEDIFF\\(.*order_date.*created_date.*\\)\\s*<=\\s*7"},
    {"name": "客户评级分档", "sql_pattern": "3-6个月"}
  ]
}
```

字段说明：

| 字段 | 用途 | 谁判 |
| --- | --- | --- |
| `track` | 四个维度之一：`attribution`、`attribution_framework`、`open_framework`、`open` | — |
| `premise` | 前提的方向和参考数字；对于 101 这类前提不成立的题，看 Agent 有没有指出来 | 程序：比对结论里的方向词和数字 |
| `factors` | 原子因素；`scored=false` 的不进分母；`bonus` 是额外发现 | 评委 |
| `facts` | 关键数字的参考值，从第二节的查询得到，每次导入数据后重算 | 程序：在本轮查询结果和结论里找这个数字 |
| `framework` | 分析思路的每一步，对应要按什么维度分组、加什么筛选 | 程序看 SQL 的 `GROUP BY` 和 `WHERE`，评委补判 |
| `knowledge` | 题目给的定义（高利贷 > 12%、闪电单 ≤ 7 天、成单 = 已交车、ROI 公式） | 程序：正则检查 SQL |

其他题的因素、关键数字和分析步骤都按第二节的表填写，由人工整理一次，两人交叉核对。

## 四、分层评测

### L0 程序部分（不调模型，每次提交）

| 对象 | DABench 用例 |
| --- | --- |
| 时间解析 | "2023 年 2 月""23年9月""2025年2月 同比""2024年11月 环比上月"，跨年同比要解析成 2024-02 |
| 安全和隐私 | 查 `dabench_raw`、查手机号或姓名要被拦住；视图里没有这些字段 |
| `facts` 参考 SQL | 每条在 `dabench` 上能执行，结果等于标注值。数据重新导入后，这组测试会先报出差异 |
| 判分函数 | 前提方向、关键数字、分析步骤、定义用法这四个判分函数，各用 3～5 个手写回答测试 |

### L1 检索（不调模型）

只有 4 张表，"找全表"几乎不会错，所以 L1 重点看**口径和取值能不能检索到**：

| 题 | 必须检索到的口径 | 必须定位到的取值 |
| --- | --- | --- |
| 48 | 销售额、毛利率 | `is_promotion` |
| 50 | 退货率 | `return_reason` = 描述与实物不符 |
| 58 | 库存周转率 | `inventory.purchase_qty` |
| 71、73 | 平均利率、高利贷 | `loan_type`、`loan_purpose`、`employment_status` |
| 101 | 线索转化漏斗、成单数 | `province` = 河南省（题目写的是"河南省"，数据里也是"河南省"） |
| 105 | 订单利润、线索 ROI | `sub_channel` = Online_AD |
| 107 | 闪电单、客户评级 | `purchase_plan` 各取值 |

加干扰表（同名备份表、相近字段）之后再测一遍，具体见分层方案的 L1。

### L3 原子查数题（新增，程序判分）

把每道题按分析思路拆成 3～5 个一问一答的小题，每题有参考 SQL，沿用 `evaluate_questions` 的严格比对和宽松比对。例如：

| 编号 | 问题 | 参考答案 |
| --- | --- | --- |
| dq-48-1 | 2023 年 1 月和 2 月的销售额和毛利率分别是多少 | 111.7 万 / 38.6%，124.5 万 / 32.3% |
| dq-48-2 | 2023 年 2 月促销订单和非促销订单的销售额和毛利率 | 70.3 万 / 27.3%，54.2 万 / 38.7% |
| dq-50-1 | 2023 年 4 月和 5 月各退货原因的退货件数 | 10 行 |
| dq-71-1 | 2023 年 8 月、9 月通过贷款按贷款类型的占比和平均利率 | 5 行 |
| dq-107-2 | 2024 年 10 月、11 月 Online_AD 渠道按客户评级的线索数和闪电单数 | 3 行 |

10 道题拆完大约 35 个小题。它们和完整归因题用同一批数字：

- 小题对、完整题错，说明问题在规划或归纳上；
- 小题就错了，说明是 SQL 或口径的问题。

这批题标 `dataset=dabench`、`kind=data`、`category=dabench_query`，单独成组计分。

### L4 下钻多轮（新增）

把分析思路改成多轮对话，每轮只问一步，例如第 107 题：

1. "2024 年 11 月创建的线索产生的闪电单比 10 月少了多少？"
2. "按二级渠道看呢？"
3. "变化最大的那个渠道，按客户评级拆开看。"

每轮的参考答案是对应的原子查数题，按会话整体判分，并记录"第几轮开始出错"。选 71、101、105、107 这 4 道分析思路最长的题，再加 74 的前 3 步，共 5 组会话。

这一层测的是：追问时能不能继承时间和筛选条件、能不能接着上一轮的结论（"变化最大的那个渠道"）往下钻。

### L5 完整归因（主分）

**跑法**

| 项 | 设置 |
| --- | --- |
| 实例 | `app-dabench`（`MYSQL_BUSINESS_DB=dabench`），评测脚本自动只选 `dataset=dabench` 的题 |
| 模式 | `analysis`，另外单独跑一组 `auto`，看路由会不会把归因题判成查询 |
| 问法 | `framework`：DABench.csv 的 `query` 列，带分析思路。`bare`：`question` 列，不带分析思路。48、50、58、73 两列一样，只跑一次 |
| 次数 | 每种问法跑 3 遍 |
| 口径对照 | `full`：现有语义层。`generic`：去掉高利贷、闪电单、客户评级、线索 ROI、成单数这 5 个题目专属口径，只能从题目文字里取定义。只在 `framework` 问法上跑 |

**每道题的判分**

| 指标 | 怎么算 | 谁判 |
| --- | --- | --- |
| 前提判断 | 结论里的方向和 `premise.direction` 一致；101 题要指出"按题目定义是上升"才算对 | 程序判方向词和数字，判不出的交给评委 |
| 数字真实率 | 结论里每个数字都能在本轮查询结果里找到（已有 `unverified_numbers`） | 程序 |
| 关键数字命中 | `facts` 里的数字在本轮查询结果中出现，误差在允许范围内 | 程序 |
| 分析框架遵从 | `framework` 每一步是否有对应的查询（维度和筛选条件对得上）；只看 `framework` 问法 | 程序为主，评委补判 |
| 知识使用 | `knowledge` 的阈值和公式是否出现在 SQL 里 | 程序 |
| 严格根因命中 | `strict=true` 且 `scored=true` 的因素全部命中 | 评委 |
| 根因召回 | 命中的计分因素数 ÷ 计分因素数 | 评委 |
| 错误归因 | 结论里给出、但和数据矛盾的"主要原因"条数 | 评委 + 程序核对数字 |
| 意图完成 | 题目要求的要素是否都答了，例如 48 题的"分别"、105 题的"从 ROI 角度"、101 题的"漏斗分析" | 评委 |

自由提问题（74、66）不算根因：

- 结论和第二节的参考数字是否一致，由程序判；
- 分析思路做了几步；
- 和基线版本两两比较（交换先后顺序各判一次），只用来看有没有退步。

**评委**

- 评委和被测模型不能是同一个。被测模型是 deepseek-chat，评委用另一家的模型。
- 输入只给题目、原子因素和 Agent 的结论加查询结果，**不给标准答案原文**，避免按字面去对。
- 每个因素输出 `hit`、`partial` 或 `miss`，并引用原文。没有引用的 `hit` 按 `miss` 算；`partial` 算 0.5，但不算严格命中。
- 校准：先跑出第一批回答（10 题 × 2 种问法 × 1 遍，约 18 份），两人独立标注，评委和人工的一致率达到 85% 以上才使用。评委提示词改动后要重新校准。

**报告格式**

每个配置一张表，所有数字都写成"题数/总数"：

### 异动注入题（扩充题量，作为留出集）

在 `dabench_synth` 库（`dabench_raw` 的副本）里埋入异动。异动由脚本决定，所以标准答案是确定的。每个数据集先做 5 道，三个数据集共 15 道：

| 数据集 | 注入方式 | 题目 | 答案 |
| --- | --- | --- | --- |
| 进销存 | 某月某个产品类别的单件成本提高 15% | 某月毛利率为什么下降 | 该类产品成本上涨 |
| 进销存 | 某月"配送延迟"的退货数量 × 4 | 某月退货率为什么升高 | 配送延迟退货增加 |
| 进销存 | 某月某几个产品的进货量 × 8 | 某月库存周转率为什么下降 | 这几个产品进货过多 |
| 信贷 | 某月某省 Car Loan 的通过率降一半 | 某月贷款通过率为什么下降 | 该省车贷通过率下降 |
| 信贷 | 某月 Student + Education Loan 的申请 × 3 | 某月平均利率为什么上升 | 学生教育贷占比增加 |
| 汽车 | 某月某城市"到店 → 试驾"的转化减半 | 某月成单为什么下降（漏斗） | 到店 → 试驾环节，该城市 |
| 汽车 | 某月 Online_SocialMedia 的线索成本 × 2 | 某月线索 ROI 为什么下降 | 该渠道成本上涨 |

**要求**

- 注入脚本带随机种子，记录注入参数，可以重新生成。
- 注入后用参考 SQL 检查：埋进去的因素必须是贡献最大的，而且比第二名至少大一倍，否则丢弃这道题。
- 生成的题目不放进任何提示词或语义层，只在发版前跑。日常调提示词只用原来的 10 道题和原子查数题。
- 运行时需要一个连 `dabench_synth` 的实例，可以用 `app-dabench` 的配置改业务库名；向量集合要单独建，避免和 `dabench` 的取值混在一起。

## 五、运行与成本

**命令（实现后才能用，参数名是计划中的，还没有验证）**

```bash
cd project && docker compose --profile dabench up -d app-dabench
docker compose run --rm --no-deps -T -v "$PWD":/work -w /work -e MYSQL_BUSINESS_DB=dabench -e MYSQL_APP_DB=dataagent_dabench -e QDRANT_COLLECTION_PREFIX=dabench app python eval/run_eval.py --mode dabench --variant framework --variant bare --repeat 3 --output eval/results/<日期>-dabench.json
```

**参数**

| 参数 | 作用 |
| --- | --- |
| `--mode dabench` | 完整归因 + 自由提问 |
| `--mode dabench-query` | 原子查数题 |
| `--mode dabench-multiturn` | 下钻多轮题 |
| `--semantic generic` | 去掉题目专属口径的对照 |
| `--judge-model` | 指定评委模型 |

**时间和费用估算**（分析流程的超时上限是 180 秒，按每题 1～3 分钟估算）

| 内容 | 次数 | 串行耗时 |
| --- | --- | --- |
| 完整归因，两种问法 × 3 遍 | 约 48 次（48、50、58、73 只有一种问法） | 50～140 分钟 |
| 原子查数题 35 道 × 3 遍 | 105 次 | 约 35 分钟 |
| 下钻多轮 5 组 × 3 遍 | 约 50 轮 | 约 20 分钟 |
| 评委 | 每份归因回答 1 次，结果按回答内容的哈希缓存 | 很少 |

全部串行要 2～3 小时，所以 `--concurrency 4` 和模型并发令牌桶（分层方案第五节 P0）要和 DABench 入口一起做。日常开发只跑 `framework` 问法 1 遍加原子查数题，大约 30 分钟。

结果文件要记录：git commit、提示词哈希、被测模型和评委模型、`variant`、`semantic`、数据集版本（导入时各表行数）、是否开缓存。

## 八、风险

| 风险 | 应对 |
| --- | --- |
| 题太少，分数波动大 | 报题数和"三遍都命中"；逐题列出 ✓✗；用异动注入题扩充 |
| 标准答案本身有错（101、107 已发现） | 每个因素都用 SQL 核对过才计分；有争议的因素保留记录、不计分；数据重新导入后重新核对 |
| 评委按关键词对答案，而不是看推理 | 不给评委标准答案原文，只给原子因素；必须引用原文；人工校准 |
| 语义层是照着题目写的，分数虚高 | `generic` 对照；异动注入题作为留出集 |
| 分析超时（180 秒） | 超时单独计数，不和"答错"混在一起；在报告里列出每题耗时的 P50 和 P95 |
| 数据重新导入后参考值变了 | `facts` 的参考 SQL 放进 L0 测试，值变了先报错 |
