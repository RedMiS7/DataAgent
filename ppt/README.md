用于存放参赛/评审用的整体介绍材料（PPT 或 PDF）。

## 交付要求

- 至少提供一种格式：`.pptx` 或导出的 `.pdf`（PDF 便于跨端查看，建议同时提交）。
- 文件名建议：`DataAgent_作品介绍_v1.pdf`。
- 页数建议 12～18 页，重点内容用图示而非大段文字。

## 内容结构（四个必答板块）

### 1. 场景背景
- 一人公司 / 小电商卖家没有专职数据分析师，经营者不会写 SQL。
- 数据分散在商品、订单、退款、广告、物流等多张表中，取数需要导出、整理、计算。
- 真实痛点举例：查“上个月哪个商品退货率最高”需要多表关联 + 口径确认。
- 目标：把一次数据查询的门槛从“会写 SQL”降为“能说清问题”。

### 2. 功能架构
- 总体架构图（复用 `docs/assets/system-architecture.png`）。
- 五步问答主流程：理解问题 → 检索上下文 → 生成 SQL → 校验并执行 → 组织结果。
- 技术栈：前端（对话页 / ECharts）、FastAPI 后端、RDS MySQL、DCS Redis、Qdrant、华为云大模型 API。
- 语义层四个向量集合：schema_items / metrics / qa_cases / entity_values。

### 3. 核心亮点
- 多路语义检索，解决业务口语与数据库字段不一致。
- 答案可核对：指标口径、时间范围、所用表、可展开 SQL。
- 从查数到归因：退货率为什么涨了，按商品/渠道/物流下钻。
- 语法校验 + 只读账号 + 列权限/脱敏视图的多层安全设计。
- 审核后入库的知识积累，避免错误案例污染检索。
- 评测驱动优化：SQL 执行结果、检索 Recall、安全拦截三类指标。
- 降级能力：Redis / 向量库不可用时主流程仍可完成。

### 4. 码道应用说明
- 码道在项目中承担的角色：架构设计讨论、后端模块生成、SQL 校验与提示词工程、测试用例、缺陷排查。
- 关键交互截图与 Prompt 出处（引用 `codearts_proof/` 中的材料）。
- 效率与质量收益：举例说明哪些模块由码道生成后人工评审修改。
- 使用边界：模型生成的 SQL 与安全规则必须经人工评审，不直接上线。
